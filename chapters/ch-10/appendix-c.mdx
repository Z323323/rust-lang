This section has been inserted at this point in the book because it is highly relevant to the concept of traits we just covered. Despite this connection, Appendix C focuses specifically on derivable traits—the standard library traits that can be quickly implemented on structs and enums using the `#[derive(Trait)]` attribute.

The contents of Appendix C have already been distributed throughout the text wherever it made the most sense. For example, the `Debug` trait was integrated into section 5.1 ('Appendix C: Derivable Traits - `Debug` for Programmer Output') the moment the `#[derive(Debug)]` attribute was introduced. Other parts of this appendix have received the same treatment and are listed below, along with the specific locations in the book where they were discussed. Nevertheless, in certain cases, we chose to expand upon the previously covered material with simple examples to help you better understand and retain the concepts.

<u>The `#[derive(Trait)]` functionality is limited to structs and enums. You cannot use the `#[derive(Trait)]` attribute on just any type; it is strictly limited to user-defined composite types (struct, enum).</u> You cannot use it on primitive types for two specific reasons:

- <u>Primitive types (like `i32`, `f64`, `bool`, and `char`) already have derivable traits like `Debug`, `Clone`, `Copy`, and `PartialEq` natively implemented by the Rust standard library out of the box.</u> There is nothing left to derive.
- The `#[derive(Trait)]` directive is an attribute macro. <u>It physically reads the fields or variants of a custom data structure to automatically generate the boilerplate code for the trait.</u> Therefore, it must be placed directly above a type declaration block in your code (e.g., `struct Type { ... }`). <u>Since you do not declare primitive types or standard library types (like `String` or `Vec`) in your own codebase, there is no declaration block for you to attach the macro to.</u>

If you create a custom struct that contains primitive types, you can use the `derive` macro on your struct. <u>The macro will succeed because it knows how to call the natively implemented traits on the inner primitives.</u>

>In various places in the book, we’ve discussed the 'derive' attribute, which you can apply to a struct or enum definition. The 'derive' attribute generates code that will implement a trait with its own default implementation on the type you’ve annotated with the `derive` syntax.

>In this appendix, we provide a reference of all the traits in the standard library that you can use with `derive`. Each section covers:

>- What operators and methods deriving this trait will enable.
>- What the implementation of the trait provided by `derive` does.
>- What implementing the trait signifies about the type.
>- The conditions in which you’re allowed or not allowed to implement the trait.
>- Examples of operations that require the trait.

>If you want different behavior from that provided by the derive attribute, consult the standard library documentation for each trait for details on how to manually implement them.

><u>The traits listed here are the only ones defined by the standard library that can be implemented on your types using `derive`.</u> Other traits defined in the standard library don’t have sensible default behavior, so it’s up to you to implement them in the way that makes sense for what you’re trying to accomplish.

>An example of a trait that can’t be derived is `Display`, which handles formatting for end users.

The implementation of the `Display` trait was analyzed in the previous section. Unlike `Debug`, <u>the `Display` trait cannot be automatically derived because the compiler cannot guess how you want your data presented to end-users</u>; you must implement it manually by defining the `fmt` method.

### Mechanics of the `fmt` Method

- The `fmt` function requires two arguments: a reference to the instance (`&self`) and a mutable reference to a formatting buffer (`&mut std::fmt::Formatter`).
- It must return a `std::fmt::Result`, which signals to the macro whether the write operation succeeded or encountered an error.
- You do not allocate and return a new `String`. Instead, you use the `write!` macro to stream your desired text directly into the formatter buffer, which is highly efficient.
    
### Implementation Example

```rust Code 10.3.1
use std::fmt;

struct Point {
    x: i32,
    y: i32,
}

impl fmt::Display for Point {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        // The write! macro writes directly to the formatter 'f'.
        // It does not return a String; it returns the required fmt::Result.
        write!(f, "Point coordinates: ({}, {}).", self.x, self.y)
    }
}

fn main() {
    let p = Point { x: 5, y: 10 };
    
    // The {} marker now automatically calls our custom fmt method!
    println!("{}", p); // 'Point coordinates: (5, 10).'
}
```

## `PartialEq` and `Eq` for Equality Comparisons

><p><u>The `PartialEq` trait allows you to compare instances of a type to check for equality and enables use of the `==` and `!=` operators.</u></p>

>Deriving `PartialEq` implements the `eq` method. <u>When `PartialEq` is derived on structs, two instances are equal only if all fields are equal, and the instances are not equal if any fields are not equal. When derived on enums, each variant is equal to itself and not equal to the other variants.</u>

>The `PartialEq` trait is required, for example, with the use of the `assert_eq!` macro (`Debug` is required too), which needs to be able to compare two instances of a type for equality.

>The `Eq` trait has no methods. <u>Its purpose is to signal that for every value of the annotated type, the value is equal to itself.</u> The `Eq` trait can only be applied to types that also implement `PartialEq`, although <u>not all types that implement `PartialEq` can implement `Eq`</u>. One example of this is floating-point number types: <u>The implementation of floating-point numbers states that two instances of the not-a-number (`NaN`) value are not equal to each other</u>.

>An example of when `Eq` is required is for keys in a `HashMap<K, V>` so that the `HashMap<K, V>` can tell whether two keys are the same.

The core difference between these two traits lies in <u>mathematical certainty</u>. <u>`PartialEq` provides the actual logic for the `==` operator, but it allows for exceptions where an object might not equal itself (a `==` could be `false`).</u> <u>`Eq`</u> is merely an empty 'marker trait' that <u>promises the compiler that equality is absolute and strictly reflexive</u> (meaning <u>a `==` is always true</u>).

### Example 1: `PartialEq`

```rust Code 10.3.2
#[derive(PartialEq)]
struct WeatherReading {
    location: String, // String implements Eq.
    temperature: f32, // f32 implements PartialEq.
}

fn main() {
    let reading1 = WeatherReading { location: String::from("Milan"), temperature: 25.5 };
    let reading2 = WeatherReading { location: String::from("Milan"), temperature: 25.5 };
    
    // This compiles and prints: 'true'.
    println!("{}", reading1 == reading2); 
}
```

### Example 2: `Eq`

If you try to add `Eq` to the exact same struct of Code 10.3.2, the code immediately crashes at compile time.

Because `Eq` is a strict mathematical guarantee that a value always equals itself, and floats violate this (because `NaN != NaN`), the Rust standard library explicitly refuses to implement `Eq` for `f32` (C-Output 10.3.3).

```rust Code 10.3.3

    temperature: f32,
```

### Example 3: `NaN`

Since the fundamental distinction between `Eq` and `PartialEq` stems directly from the `NaN` (Not a Number) value and its behavioral implications, Code 10.3.4 demonstrates exactly how `NaN` values are produced. Observing this behavior directly makes it much easier to understand what `NaN` is and why Rust's architecture was intentionally designed to handle it this way.

<CodeGroup>

```rust Code 10.3.4
fn main() {
    // 1. Zero / Zero
    let zero = 0.0;
    let nan1 = zero / zero;

    // 2. Square root of a negative number
    let negative: f64 = -1.0;
    let nan2 = negative.sqrt();

    // 3. Infinity minus Infinity
    let inf = f64::INFINITY;
    let nan3 = inf - inf;

    // This is the exact reason floats break the `Eq` trait:
    // NaN is NEVER equal to anything, not even itself.
    println!("Is NaN equal to NaN? {}", nan1 == nan1); // Prints: 'false'.
}
```

## `PartialOrd` and `Ord` for Ordering Comparisons

>The `PartialOrd` trait allows you to compare instances of a type for sorting purposes. <u>A type that implements `PartialOrd` can be used with the `<`, `>`, `<=`, and `>=` operators. You can only apply the `PartialOrd` trait to types that also implement `PartialEq`.</u>

><u>Deriving `PartialOrd` implements the `partial_cmp` method, which returns an `Option<Ordering>` that will be `None` when the values given don’t produce an ordering.</u> An example of a value that doesn’t produce an ordering, even though most values of that type can be compared, is the `NaN` floating point value. <u>Calling `partial_cmp` with any floating-point number and the `NaN` floating-point value will return `None`.</u>

>When derived on structs, `PartialOrd` compares two instances by comparing the value in each field in the order in which the fields appear in the struct definition. When derived on enums, variants of the enum declared earlier in the enum definition are considered less than the variants listed later.

If the first field of Struct A is greater than the first field of Struct B, the comparison stops immediately. Struct A is declared the greater of the two. The compiler completely ignores the second field, regardless of how small or large it is. The second field is only ever evaluated if the first fields are exactly equal.

If the default top-to-bottom evaluation does not fit your business logic (for example, you want to prioritize comparing the second field before the first), you must remove `#[derive(PartialOrd)]` and implement it manually.

Because this is `PartialOrd` (which handles types like floats that might be `NaN`), the `partial_cmp` method must return an `Option<Ordering>` instead of a direct `Ordering`.

>The `PartialOrd` trait is required, for example, for the `gen_range` method from the `rand` crate that generates a random value in the range specified by a range expression.

><u>The `Ord` trait allows you to know that for any two values of the annotated type, a valid ordering will exist. The `Ord` trait implements the `cmp` method, which returns an `Ordering` rather than an `Option<Ordering>` because a valid ordering will always be possible.</u> You can only apply the `Ord` trait to types that also implement `PartialOrd` and `Eq` (and `Eq` requires `PartialEq`). When derived on structs and enums, `cmp` behaves the same way as the derived implementation for `partial_cmp` does with `PartialOrd`.

>An example of when `Ord` is required is when storing values in a `BTreeSet<T>`, a data structure that stores data based on the sort order of the values.

The `Ord` trait was previously demonstrated in the final example of Ch. 2, when the user's guess was compared against the randomly generated secret number. In that scenario, the `cmp` method was called directly on `guess`. Because `guess` was explicitly typed as a `u32`, and primitive integer types natively implement `Ord`, calling this method was perfectly valid. As you may recall, the result of the `cmp` method is always a variant of the `Ordering` enum.

To fully understand how this works under the hood, here is a detailed breakdown of the implementation of the `Ordering` enum, the `Ord` trait, and its `cmp` method.

### The `Ordering` Enum

`Ordering` is a simple standard library enum designed to represent the exact mathematical result of a comparison.

```rust Code 10.3.5
pub enum Ordering {
    Less,
    Equal,
    Greater,
}
```

### The `Ord` Trait

```rust Code 10.3.6
pub trait Ord: Eq + PartialOrd {
    fn cmp(&self, other: &Self) -> Ordering;
}
```

Code 10.3.6 introduces a syntax we haven't encountered yet: <u>defining a (double) trait bound directly within the trait declaration itself</u>. <u>This structure enforces the bounds universally, ensuring they apply even to primitive types, which do not use the generic `<T: Trait>` syntax.</u>

### The `cmp` Method

Here is the actual implementation from the Rust standard library (`core::cmp`), slightly cleaned up by removing internal compiler annotations for better readability.

```rust Code 10.3.7
use std::cmp::Ordering;

// 1. The macro is defined to accept a list of types ($t:ty).
macro_rules! ord_impl {
    ($($t:ty)*) => ($(
        
        // 2. It implements the Ord trait for whatever type is passed in.
        impl Ord for $t {
            #[inline]
            fn cmp(&self, other: &$t) -> Ordering {
                
                // 3. The actual comparison logic using standard operators
                if *self < *other {
                    Ordering::Less
                } else if *self == *other {
                    Ordering::Equal
                } else {
                    Ordering::Greater
                }
            }
        }
        
    )*)
}

// 4. The macro is invoked once, stamping out the implementation 
// for every single primitive integer type in the language.
ord_impl! { usize u8 u16 u32 u64 u128 isize i8 i16 i32 i64 i128 }
```

Code 10.3.7 introduces a couple features we haven't analyzed yet: a macro structure that does not rely on commas (`,`) to separate types, alongside the `#[inline]` attribute.

In Rust macros, whatever punctuation you put immediately before the `*` becomes the required separator.

- If the code said `$($t:ty),*`, the compiler would strictly require commas: `u8, u16, u32`.
- If it said `$($t:ty);*`, it would require semicolons: `u8; u16; u32`.
- Because the code is just `$($t:ty)*` (<u>with nothing before the asterisk</u>), <u>the compiler defaults to standard whitespace</u>. It treats spaces, tabs, and newlines as the separators, allowing the standard library developers to cleanly list the types as `usize u8 u16 u32 ...`.

### The `#[inline]` Attribute

When a program calls a function, the CPU has to save its current state, jump to a different memory address to execute the function, and then jump back. For a massive function, this overhead is unnoticeable. But for a microscopic function like `cmp`—which just evaluates an `if`/`else` statement—the jump itself takes longer than the actual math.

The `#[inline]` attribute is a direct hint to the compiler: 'Do not treat this as a real function call. Whenever someone calls `.cmp()`, just copy-paste the internal `if`/`else` logic directly into their code'. <u>This eliminates the function call overhead, making standard integer comparisons blazing fast.</u>

## `Clone` and `Copy` for Duplicating Values

Refer to [[4.2 - Memory and Allocation - Appendix C: Derivable Traits - `Clone` and `Copy` for Duplicating Values](/chapters/ch-4/memory-and-allocation#appendix-c-derivable-traits-clone-and-copy-for-duplicating-values)].

Although this concept was introduced earlier, this paragraph provides a deeper, more practical explanation by walking through two simple examples. We will take the same approach in the following paragraph.

Here is the breakdown of the mechanical differences between the `Clone` and `Copy` traits using practical examples.

### Example 1: Deriving `Clone` (Explicit Duplication)

The `Clone` trait allows you to duplicate an object by explicitly invoking the `clone` method. <u>If a struct contains types that allocate memory on the heap (like `String`), you can only derive `Clone`, not `Copy`.</u>

```rust Code 10.3.8
// We only derive Clone. 
// We cannot derive Copy because String does not implement Copy.
#[derive(Clone)]
struct User {
    name: String,
}

fn main() {
    let user1 = User { name: String::from("Alice") };
    
    // If we did `let user2 = user1;`, 'user1' would be MOVED
    // and would no longer be usable due to ownership rules.
    
    // We explicitly invoke 'clone' to perform a deep copy.
    let user2 = user1.clone(); 

    // Both variables are valid and usable.
    println!("Original: {}, Copy: {}", user1.name, user2.name);
}
```

Here, <u>the duplication is explicit and potentially expensive</u>. When you call `clone`, Rust goes to the heap, allocates new memory for the new `String`, and copies the data byte by byte.

### Example 2: Deriving `Copy` (Implicit Duplication)

The `Copy` trait radically changes the compiler's behavior: it transforms an ownership transfer (a move) into an automatic, implicit duplication. <u>You can only derive `Copy` if all the fields within your struct reside entirely on the stack (like integers, floats, and booleans).</u>

Because `Copy` requires the type to also implement `Clone` (it is a super-trait), you must derive both.

```rust Code 10.3.9
// We derive both Copy and Clone.
// This works because u32 resides entirely on the stack.
#[derive(Copy, Clone)]
struct Point {
    x: u32,
    y: u32,
}

fn main() {
    let point1 = Point { x: 10, y: 20 };
    
    // We are NOT calling 'clone'!
    // Thanks to the Copy trait, the assignment does not move ownership.
    // It implicitly copies the stack bits of 'point1' directly into 'point2'.
    let point2 = point1; 

    // 'point1' is still perfectly valid.
    println!("Point 1: x={}, y={}", point1.x, point1.y);
    println!("Point 2: x={}, y={}", point2.x, point2.y);
}
```

## Why is `Clone` a Supertrait of `Copy`?

First of all, <u>a **supertrait** in Rust establishes a strict prerequisite for another trait</u>. <u>It dictates that before a type is legally allowed to implement a specific trait, it must first implement its supertrait.</u> You define a supertrait using the colon `:` syntax, which looks <u>exactly like applying a trait bound to a generic type</u>.

<u>The `Ord` trait we observed earlier (`pub trait Ord: Eq + PartialOrd`) actually relies on `Eq` and `PartialOrd` as its supertraits!</u> Ultimately, as noted before, <u>a supertrait is simply a trait bound defined directly on the trait declaration itself, establishing a universal prerequisite before the trait can be implemented for any specific type</u>.

<Warning>
The word 'super' is famously counterintuitive here. It naturally sounds like it should refer to the 'biggest' or most comprehensive trait that encompasses the others (which would be `Ord`). However, in type architecture, 'super' refers to the parent foundation that everything else is built upon. Therefore, mathematically and in the Rust documentation, <u>`Eq` and `PartialOrd` are the supertraits of `Ord`</u>.
</Warning>

### Core Characteristics of Supertraits

- **Prerequisite, Not Inheritance**: In Object-Oriented Programming, a child class automatically inherits methods and data from a parent class. <u>Rust supertraits do not inherit.</u> The declaration `trait SubTrait: SuperTrait` simply means: 'It is illegal for a type to implement `SubTrait` unless it has already implemented `SuperTrait`'.
- **No Automatic Implementation**: The compiler will not automatically write or generate the `SuperTrait` implementation for you. <u>If you want your struct to have `SubTrait`, you are forced to write two entirely separate `impl` blocks</u>—one for the supertrait and one for the sub-trait.
- **Guaranteed Method Access**: If you write a generic function that requires the sub-trait (e.g., `fn execute<T: SubTrait>(item: &T)`), the compiler automatically knows that item possesses all the methods from `SuperTrait`. <u>You do not need to write redundant bounds like `<T: SuperTrait + SubTrait>`.</u>

Code 10.3.10 below has been specifically designed to clarify most of the trait concepts introduced up to this point. Readers are strongly encouraged to review Code 10.3.10 carefully and ensure they understand it thoroughly.

<CodeGroup>
```rust Code 10.3.10
trait Powered {
    fn power_on(&self);
}

trait Illuminated: Powered {
    fn illuminate(&self);
}

struct Battery;

impl Powered for Battery {
    fn power_on(&self) {
        println!("Battery: Delivering electrical current.");
    }
}

struct Gadget<T> {
    component: T,
}

// Implementing Powered for Gadget<T>
// (We delegate the power action to the inner type T, provided T is Powered).
impl<T: Powered> Powered for Gadget<T> {
    fn power_on(&self) {
        println!("Gadget system initializing...");
        self.component.power_on();
    }
}

// Implementing Illuminated for Gadget<T>.
// Because Illuminated requires Powered as a supertrait, 
// Rust's compiler checks: 'Does Gadget<T> implement Powered?' 
// Yes, we just implemented it above! Therefore, this compiles successfully.
impl<T: Powered> Illuminated for Gadget<T> {
    fn illuminate(&self) {
        println!("Gadget: LED lights are now glowing!");
    }
}

// ==================================
// GUARANTEED METHOD ACCESS IN ACTION
// ==================================
// Look at the trait bound: we ONLY ask for `T: Illuminated`.
// We do NOT write `T: Powered + Illuminated`.
fn activate_device_fully<T: Illuminated>(device: &T) {
    println!("--- Starting full activation sequence ---");
    
    // 1. We can call the subtrait method directly.
    device.illuminate();
    
    // 2. MAGIC: We can ALSO call the supertrait method (`power_on`),
    // even though `Powered` is not explicitly mentioned in `<T: Illuminated>`.
    // The compiler guarantees `T` has it because `Illuminated` requires it.
    device.power_on(); 
}

fn main() {
    // We create a Gadget containing our Battery.
    let smart_gadget = Gadget { 
        component: Battery 
    };

    // Because Gadget implements Illuminated (and by extension, Powered), 
    // we can invoke methods from both traits on the wrapper!
    smart_gadget.power_on();   // Powered method (delegated to Battery)
    smart_gadget.illuminate(); // Illuminated method (native to Gadget)
    
    // Passing our gadget into a function that only requests Illuminated.
    activate_device_fully(&smart_gadget);
}
```

To truly understand why the compiler rejects an unconditional implementation like `impl<T> Illuminated for Gadget<T>`, we have to look at how Rust connects supertrait obligations with conditional implementations.

### 1. The Broken Promise of the Supertrait

Remember the core rule of supertraits we established earlier: <u>a type cannot implement a subtrait unless it already implements the supertrait</u>.

In Code 10.3.10:

- `Illuminated` is a subtrait of `Powered` (`trait Illuminated: Powered`). This means every type implementing `Illuminated` is legally obligated to implement `Powered` as well.
- We implemented `Powered` for our generic wrapper <u>conditionally</u>: `impl<T: Powered> Powered for Gadget<T>`. This tells the compiler: <u>'A `Gadget<T>` can provide power, but only if its inner type `T` also implements `Powered`'</u>.

### 2. What Happens When You Remove the Bound?

If you try to write `impl<T> Illuminated for Gadget<T>` (removing `T: Powered`), you are telling the compiler: <u>'I want every single `Gadget<T>` to be illuminated, for any arbitrary type `T`, even if `T` knows nothing about power'</u>.

The compiler immediately spots a fatal contradiction:

- The Subtrait Rule: Every `Gadget<T>` that implements `Illuminated` must also implement `Powered`.
- The Reality Check: According to your `Powered` implementation, `Gadget<T>` only implements `Powered` if `T: Powered`.

<u>If you pass a type `T` that does not implement `Powered`, your `Gadget<T>` would somehow be `Illuminated` without being `Powered`.</u> This directly violates the `Illuminated: Powered` supertrait contract.

### 3. The Compiler's Rule

To keep the type system sound, Rust enforces a strict rule: The trait bounds on a subtrait implementation must be at least as restrictive as (or consistent with) the bounds required by its supertrait.

Because `Gadget<T>` relies on `T: Powered` to fulfill its supertrait obligations, <u>any implementation of `Illuminated` for `Gadget<T>` must also carry that exact same `T: Powered` bound</u>.

### The Verdict: `Clone` vs. `Copy`

At first glance, making `Clone` a supertrait of `Copy` (`pub trait Copy: Clone {}`) feels completely backward. `Copy` is a primitive, invisible bitwise copy, while `Clone` is a complex, explicit deep copy. Why does the simple trait require the complex one?

It comes down to a strict mathematical relationship and API consistency: everything that can be implicitly copied must logically also be explicitly cloneable.

### 1. The 'Subset' Logic

<u>Think of `Clone` as the universal category of 'things that can be duplicated'.</u> <u>`Copy` is just a highly specialized, restricted sub-category of `Clone` where the duplication happens to be trivial</u> (a simple memory copy).

If a type is simple enough that the compiler can copy it invisibly behind your back (`Copy`), it is mathematically illogical to say you cannot manually request a copy using `clone`. By forcing `Copy` to require `Clone`, Rust ensures that any `Copy` type automatically satisfies the broader, universal definition of 'can be duplicated'.

### 2. Generic API Compatibility

Imagine you are using a third-party function that requires explicit duplication:

```rust Code 10.3.11
fn process_data<T: Clone>(data: &T) {
    let duplicated = data.clone();
    // ...
}
```

<u>If `Copy` did not require `Clone`, primitive types like `u32` or your custom stack-only structs would not be allowed in this function, because being `Copy` wouldn't guarantee they are `Clone`.</u> You would have to write duplicate APIs: one for `Copy` types and one for `Clone` types. By making `Copy` a supertrait of `Clone`, the Rust compiler guarantees that whenever an API asks for `Clone`, you can safely pass a `Copy` type into it.

### 3. Semantic Consistency

When a type implements both `Copy` and `Clone`, Rust expects their behavior to be absolutely identical. <u>For a `Copy` type, the `Clone` implementation is just a manual trigger for the exact same bitwise copy.</u>

```rust Code 10.3.12
// The standard manual implementation of Clone for a Copy type
impl Clone for MyCopyStruct {
    fn clone(&self) -> Self {
        *self // Just dereference and trigger the bitwise Copy.
    }
}
```

If `Copy` did not strictly depend on `Clone`, a developer could theoretically create a struct where implicit copying (`let y = x`) does a fast bitwise copy, but explicit cloning (`let y = x.clone()`) connects to a database, allocates memory, or generates a random number. By binding them together, Rust enforces a semantic contract: <u>if a type is `Copy`, its `clone` method must do nothing more than duplicate the bits</u>.

In short, `Copy` does not inherit complexity from `Clone`. Instead, it guarantees that it fits perfectly inside `Clone`'s universe, ensuring your simple structs work seamlessly with generic code that expects data to be duplicable.

## `Hash` for Mapping a Value to a Value of Fixed Size

Refer to [[8.3 - Storing Keys with Associated Values in Hash Maps - Appendix C: Derivable Traits - `Hash` for Mapping a Value to a Value of Fixed Size](/chapters/ch-8/hash-maps#appendix-c-derivable-traits-hash-for-mapping-a-value-to-a-value-of-fixed-size)].

To use a custom struct as a key in a `HashMap`, deriving `Hash` alone is not enough. <u>The Rust standard library strictly requires the key to also implement `Eq` and `PartialEq`. This is because the hash map first uses the hash to find the correct memory bucket, and then uses mathematical equality (`Eq`) to verify it has found the exact matching key in case of a hash collision.</u>

<CodeGroup>
```rust Code 10.3.11
use std::collections::HashMap;

// We must derive all three traits to use this struct as a HashMap key.
#[derive(Hash, Eq, PartialEq)]
struct Employee {
    id: u32,
    department: String,
}

fn main() {
    // Create a new HashMap where the key is our custom Employee struct.
    let mut employee_roles = HashMap::new();

    let emp1 = Employee { id: 101, department: String::from("Sales") };
    let emp2 = Employee { id: 102, department: String::from("IT") };

    // Insert the structs as keys, and their job titles as values.
    employee_roles.insert(emp1, "Sales Manager");
    employee_roles.insert(emp2, "System Administrator");

    // Let's try to retrieve a value. We create a brand new instance 
    // but with the exact same data as 'emp1'.
    let search_key = Employee { id: 101, department: String::from("Sales") };
    
    // The HashMap hashes `search_key`, finds the matching bucket, 
    // and uses Eq to confirm it perfectly matches the original 'emp1'.
    if let Some(role) = employee_roles.get(&search_key) {
        println!("The role for this employee is: {}", role);
    }
}
```

One might wonder why equality (`Eq`) needs to be implemented on the custom key type itself, given that the key is hashed into an integer. The HashMap retains the original keys in its buckets. <u>While the `hash` function is used solely for rapid indexing and bucket location, the final verification during a lookup or collision resolution requires a direct `==` comparison between the stored custom key and the search key</u>—which is why `Eq` must be implemented on the custom type.

## `Default` for Default Values

><u>The `Default` trait allows you to create a default value for a type. Deriving `Default` implements the `default` function.</u> The derived implementation of the `default` function calls the `default` function on each part of the type, meaning all fields or values in the type must also implement `Default` to derive `Default`.

>The `Default::default` function is commonly used in combination with the struct update syntax in Ch. 5. You can customize a few fields of a struct and then set and use a default value for the rest of the fields by using `..Default::default()`.

>The `Default` trait is required when you use the method `unwrap_or_default` on `Option<T>` instances, for example. <u>If the `Option<T>` is `None`, the method `unwrap_or_default` will return the result of `Default::default` for the type `T` stored in the `Option<T>`.</u>

Here is a complete, practical example that combines both concepts: using `..Default::default()` with struct update syntax, and utilizing `unwrap_or_default()` on an `Option<T>` instance.

<CodeGroup>
```rust Code 10.3.12
#[derive(Debug, Default)]
struct Settings {
    host: String,
    port: u16,
    timeout: u32,
    debug_mode: bool,
}

fn main() {
    // ----------------------------------------------------
    // PART 1: Struct Update Syntax with Default::default()
    // ----------------------------------------------------
    // We want a custom configuration, but instead of specifying every field,
    // we explicitly set 'port' and 'debug_mode', and let '..Default::default()'
    // automatically fill in the remaining fields with their standard defaults 
    // (e.g., empty String for host, 0 for timeout).
    let custom_settings = Settings {
        port: 8080,
        debug_mode: true,
        ..Default::default()
    };

    println!("Custom Settings: {:#?}", custom_settings);

    // -------------------------------------------
    // PART 2: unwrap_or_default() on an Option<T>
    // -------------------------------------------
    // Imagine we try to load settings from a config file, but the file is missing,
    // resulting in a None value.
    let user_config_file: Option<Settings> = None;

    let active_settings = user_config_file.unwrap_or_default();

    println!("Active Settings (Fallback): {:#?}", active_settings);
}
```
