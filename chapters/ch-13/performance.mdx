>To determine whether to use loops or iterators, you need to know which implementation is faster: the version of the `search` function with an explicit `for` loop or the version with iterators.

>We ran a benchmark by loading the entire contents of 'The Adventures of Sherlock Holmes' by Sir Arthur Conan Doyle into a `String` and looking for the word `the` in the contents. Here are the results of the benchmark on the version of search using the `for` loop and the version using iterators:

```text
test bench_search_for  ... bench:  19,620,300 ns/iter (+/- 915,700)
test bench_search_iter ... bench:  19,234,900 ns/iter (+/- 657,200)
```

>The two implementations have similar performance! We won’t explain the benchmark code here because the point is not to prove that the two versions are equivalent but to get a general sense of how these two implementations compare performance-wise.

>For a more comprehensive benchmark, you should check using various texts of various sizes as the contents, different words and words of different lengths as the query, and all kinds of other variations. The point is this: <u>Iterators, although a high-level abstraction, get compiled down to roughly the same code as if you’d written the lower-level code yourself</u>. Iterators are one of Rust’s **zero-cost abstractions**, by which <u>we mean that using the abstraction imposes no additional runtime overhead</u>. This is analogous to how Bjarne Stroustrup, the original designer and implementor of C++, defines zero-overhead in his 2012 ETAPS keynote presentation 'Foundations of C++':

<Info>
In general, C++ implementations obey the zero-overhead principle: What you don’t use, you don’t pay for. And further: What you do use, you couldn’t hand code any better.
</Info>

><u>In many cases, Rust code using iterators compiles to the same assembly you’d write by hand. Optimizations such as loop unrolling and eliminating bounds checking on array access apply and make the resultant code extremely efficient.</u> Now that you know this, you can use iterators and closures without fear! They make code seem like it’s higher level but don’t impose a runtime performance penalty for doing so.

## Benchmark Tests

We will dive into benchmark tests right here, as they are a fundamental concept in Rust and any performance-oriented language. To analyze them, we'll head over to [[doc.rust-lang.org/unstable-book/library-features/test.html](https://doc.rust-lang.org/unstable-book/library-features/test.html)], because the Rust Book doesn't cover them directly—<u>they are an unstable feature</u>.

### Native Benchmarking with Rust's Unstable Test Library

>The internals of the test crate are unstable, behind the `test` flag. The most widely used part of the `test` crate are benchmark tests, which can test the performance of your code. Let’s make our _src/lib.rs_ look like this (comments elided):

```rust Code 13.4.1
#![feature(test)]

extern crate test;

pub fn add_two(a: i32) -> i32 {
    a + 2
}

#[cfg(test)]
mod tests {
    use super::*;
    use test::Bencher;

    #[test]
    fn it_works() {
        assert_eq!(4, add_two(2));
    }

    #[bench]
    fn bench_add_two(b: &mut Bencher) {
        b.iter(|| add_two(2));
    }
}
```

>Note the `test` feature gate, which enables this unstable feature.

>We’ve imported the `test` crate, which contains our benchmarking support. We have a new function as well, with the `bench` attribute. Unlike regular tests, which take no arguments, <u>benchmark tests take a `&mut Bencher`</u>. <u>This `Bencher` provides an `iter` method, which takes a closure. This closure contains the code we’d like to benchmark.</u>

><p><u>We can run benchmark tests with `cargo bench`.</u></p>

<CodeGroup>
```bash Command 13.4.1
cargo bench
```
```text Output 13.4.1
   Compiling adder v0.0.1 (file:///home/steve/tmp/adder)
     Running target/release/adder-91b3e234d4ed382a

running 2 tests
test tests::it_works ... ignored
test tests::bench_add_two ... bench:         1 ns/iter (+/- 0)

test result: ok. 0 passed; 0 failed; 1 ignored; 1 measured
```
</CodeGroup>

><u>Our non-benchmark test was ignored.</u> You may have noticed that <u>`cargo bench` takes a bit longer than `cargo test`</u>. <u>This is because Rust runs our benchmark a number of times, and then takes the average. Because we’re doing so little work in this example, we have a `1 ns/iter (+/- 0)`, but this would show the variance if there was one.</u>

>Advice on writing benchmarks:

>- Move setup code outside the `iter` loop; only put the part you want to measure inside.
>- Make the code do 'the same thing' on each iteration; do not accumulate or change state.
>- Make the outer function idempotent too; the benchmark runner is likely to run it many times.
>- Make the inner `iter` loop short and fast so benchmark runs are fast and the calibrator can adjust the run-length at fine resolution.
>- Make the code in the `iter` loop do something simple, to assist in pinpointing performance improvements (or regressions).

>There’s another tricky part to writing benchmarks: benchmarks compiled with optimizations activated can be dramatically changed by the optimizer so that the benchmark is no longer benchmarking what one expects. <u>For example, the compiler might recognize that some calculation has no external effects and remove it entirely.</u>

<CodeGroup>
```rust Code 13.4.2
#![feature(test)]

extern crate test;
use test::Bencher;

#[bench]
fn bench_xor_1000_ints(b: &mut Bencher) {
    b.iter(|| {
        (0..1000).fold(0, |old, new| old ^ new);
    });
}
```
```text B-Output 13.4.2
running 1 test
test bench_xor_1000_ints ... bench:         0 ns/iter (+/- 0)

test result: ok. 0 passed; 0 failed; 0 ignored; 1 measured
```
</CodeGroup>

>The benchmarking runner offers two ways to avoid this. Either, <u>the closure that the `iter` method receives can return an arbitrary value which forces the optimizer to consider the result used and ensures it cannot remove the computation entirely</u>. This could be done for the example above by adjusting the `b.iter` call to

```rust
b.iter(|| {
    // Note lack of `;` (could also use an explicit `return`).
    (0..1000).fold(0, |old, new| old ^ new)
});
```

>Or, <u>the other option is to call the generic `test::black_box` function, which is an opaque 'black box' to the optimizer and so forces it to consider any argument as used</u>.

<CodeGroup>
```rust Code 13.4.3
#![feature(test)]

extern crate test;

b.iter(|| {
    let n = test::black_box(1000);

    (0..n).fold(0, |a, b| a ^ b)
})
```
```text B-Output 13.4.3
running 1 test
test bench_xor_1000_ints ... bench:       131 ns/iter (+/- 3)

test result: ok. 0 passed; 0 failed; 0 ignored; 1 measured
```
</CodeGroup>

><p><u>Neither of these read or modify the value, and are very cheap for small values. Larger values can be passed indirectly to reduce overhead (e.g. `black_box(&huge_struct)`).</u></p>

>Performing either of the above changes gives B-Output 13.4.3. However, the optimizer can still modify a testcase in an undesirable manner even when using either of the above.

### Production-Grade Benchmarking with Criterion

Let's write a couple of benchmark tests to see if the `minigrep` implementation using iterators and closures is faster than a traditional loop-based approach—one that uses a `for` loop inside `search` and `search_case_insensitive` and returns an `Vec<String>`.

Before we can do that, we need to code this alternative implementation and set up our project structure. Below, you will find the modifications required to put the loop-based solution in place.

First, create a new directory named _bin_ inside _src_ and move your _main.rs_ file there. You will need to split the two implementations into separate binaries; for instance, I named mine _main_no_closures.rs_ and _main_with_closures.rs_ so the outputs make it clear what we are testing.


Next, we can keep a single _lib.rs_ file while providing two different versions of both `search` and `search_case_insensitive` (I named the loop-based variants `search_no_cl` and `search_case_insensitive_no_cl`).

- _src/bin/main_no_closures.rs_

  ```rust main_no_closures.rs
  use minigrep::*;
  
  // --snip--
  
  fn run(mut config: Config) -> Result<(), Box<dyn Error>> {
      let contents = fs::read_to_string(config.file_path)?;
  
      let result = if config.ignore_case {
          search_case_insensitive_no_cl(&mut config.query, &contents)
      } else {
          search_no_cl(&config.query, &contents)
      };
  
      for line in result.iter() {
          println!("{line}");
      }
  
      Ok(())
  }
  ```
  
- _src/lib.rs_

  ```rust lib.rs
  pub fn search<'a>(query: &'a String, contents: &'a str) -> Box<dyn Iterator<Item = &'a str> + 'a> {
      Box::new(contents.lines().filter(|&line| line.contains(&*query)))
  }

  pub fn search_no_cl(query: &String, contents: &str) -> Vec<String> {
      let mut vec: Vec<String> = vec![];
  
      for line in contents.lines() {
          if line.contains(&*query) {
              vec.push(String::from(line));
          }
      }
  
      vec
  }

  pub fn search_case_insensitive<'a>(
      query: &'a mut String,
      contents: &'a str,
  ) -> Box<dyn Iterator<Item = &'a str> + 'a> {
      *query = query.to_lowercase();
  
      Box::new(
          contents
              .lines()
              .filter(|&line| line.to_lowercase().contains(&*query)),
      )
  }

  pub fn search_case_insensitive_no_cl(query: &mut String, contents: &str) -> Vec<String> {
      let mut vec: Vec<String> = vec![];
      *query = query.to_lowercase();
  
      for line in contents.lines() {
          if line.to_lowercase().contains(&*query) {
              vec.push(String::from(line));
          }
      }
  
      vec
  }
  ```

Now let's write our benchmark tests. Be sure to modify your _Cargo.toml_ file to match the configuration shown below.

We are doing this because the native benchmarking features we looked at earlier require an unstable (nightly) version of Rust, which we aren't using right now. However, <u>this is actually an advantage: the `criterion` crate is designed specifically for robust, professional-grade benchmarking and works seamlessly on stable Rust, making it a much more reliable solution than the built-in unstable alternative</u>.
  
  
```toml minigrep/Cargo.toml
[package]
name = "minigrep"
version = "0.1.0"
edition = "2024"

[dependencies]

[dev-dependencies]
criterion = "0.5"

[[bench]]
name = "benchmark_tests"
harness = false
```

Setting `harness = false` in your _Cargo.toml_ file disables the language's default, built-in test and benchmark runner. This configuration is essential when using third-party benchmarking libraries like `Criterion`.

You will also need to create a _benches_ directory at the root of your project (alongside _src_) and place the _benchmark_tests.rs_ file inside it. I have also included a _setup_ directory within _benches_ containing a _mod.rs_ file to demonstrate a common configuration mechanism for tests and benchmarks—something the Rust Book doesn't provide a working example of in Ch. 11.

```bash Command 13.4.4
cd ~/rust_projects/minigrep &&
mkdir benches &&
touch benches/benchmark_tests.rs &&
cd benches &&
mkdir setup &&
touch setup/mod.rs
```

Insert the following contents into the _benchmark_tests.rs_ and _setup/mod.rs_ files, respectively.

- _benchmark_tests.rs_

  ```rust benches/benchmark_tests.rs
  use criterion::{Criterion, criterion_group, criterion_main};
  
  mod setup;
  
  fn bench_no_closures(c: &mut Criterion) {
      let mut no_cl_binary = setup::command(
          "/var/home/z561/rust_projects/minigrep/target/debug/main_no_closures",
          vec![
              String::from("target/debug/main_no_closures"),
              String::from("to"),
              String::from("poem.txt"),
          ],
      );
  
      c.bench_function("no_closures solution", |b| {
          b.iter(|| {
              no_cl_binary
                  .output()
                  .expect("Execution error on main_no_closures")
          })
      });
  }
  
  fn bench_closures(c: &mut Criterion) {
      let mut cl_binary = setup::command(
          "/var/home/z561/rust_projects/minigrep/target/debug/main_with_closures",
          vec![
              String::from("target/debug/main_with_closures"),
              String::from("to"),
              String::from("poem.txt"),
          ],
      );
  
      c.bench_function("closures solution", |b| {
          b.iter(|| {
              cl_binary
                  .output()
                  .expect("Execution error on main_with_closures")
          })
      });
  }
  
  criterion_group!(benches, bench_no_closures, bench_closures);
  criterion_main!(benches);
  ```

- _setup/mod.rs_

  ```rust setup/mod.rs
  use std::process::Command;
  
  pub fn command(path: &str, args: Vec<String>) -> Command {
      let mut command = Command::new(path);
  
      command.args(args);
  
      command
  }
  ```

At this point, it is important to make one final observation. <u>The benchmark tests presented in this section are meant purely for educational purposes.</u> Running them a few times is enough to see that the performance difference between the two implementations is practically negligible.

Furthermore, <u>you would normally benchmark code in a much more granular manner than what we did in _benchmark_tests.rs_</u>. <u>Benchmarking the execution of an entire binary is not idiomatic</u>; we took this approach here simply to demonstrate additional capabilities offered by Rust and Cargo.

Finally, please exercise caution when using `Command`. In a real-world production environment, spawning external processes via `Command` can be extremely dangerous if not handled securely.
