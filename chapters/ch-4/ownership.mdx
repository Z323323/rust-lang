><p><u>Ownership is a set of rules that govern how a Rust program manages memory. If any of the rules are violated, the program won’t compile. None of the features of ownership will slow down your program while it’s running.</u></p>

## The Stack and the Heap

>In a systems programming language like Rust, whether a value is on the stack or the heap affects how the language behaves and why you have to make certain decisions.

><p>Both the stack and the heap are parts of memory available to your code to use at runtime, but they are structured in different ways. The stack stores values in the order it gets them and removes the values in the opposite order. This is referred to as <u>l</u>ast <u>i</u>n, <u>f</u>irst <u>o</u>ut (LIFO). Adding data is called <u>pushing onto the stack</u>, and removing data is called <u>popping off the stack</u>. <u>All data stored on the stack must have a known, fixed size.</u></p>
>   <div style={{ display: 'flex', marginTop: '0.5rem', color: '#009B77' }}>
>     <span>↘</span>
>     <div>
>      <p>All of the scalar types which we explored in section 3.3 have a known, fixed size at compile time. Because of this, <u>they are stored directly on the stack and inherently implement the `Copy` trait</u>! Regarding the types discussed in section 3.3: 'Tuples implements `Copy` if they only contain types that also implement `Copy`. For example, `(i32, i32)` implements `Copy`, but `(i32, String)` does not'. Arrays can also contain elements that do not implement the `Copy` trait. In such cases, arrays exhibit the exact same behavior as tuples.</p>
>     </div>
>   </div>

><p><u>Data with an unknown size at compile time or a size that might change must be stored on the heap instead. When you put data on the heap, you request a certain amount of space. The memory allocator finds an empty spot in the heap that is big enough, marks it as being in use, and returns a pointer, which is the address of that location.</u> This process is called <u>allocating on the heap</u> (pushing values onto the stack is not considered allocating). <u>Because the pointer to the heap is a known, fixed size, you can store the pointer on the stack, but when you want the actual data, you must follow the pointer.</u></p>
>   <div style={{ display: 'flex', marginTop: '0.5rem', color: '#009B77' }}>
>     <span>↘</span>
>     <div>
>      <p>Types that manage dynamically sized data (such as `String`) must allocate their underlying memory on the heap. Consequently, they cannot implement the `Copy` trait. As observed in the latter part of section 3.2: the address (along with the string's metadata) that gets moved when `=` is used without `&` is stored on the STACK. Specifically, this address stored on the STACK points to a specific region of the HEAP memory.</p>
>     </div>
>   </div>

><p><u>Pushing to the stack is faster than allocating on the heap because the allocator never has to search for a place to store new data; that location is always at the top of the stack. Comparatively, allocating space on the heap requires more work because the allocator must first find a big enough space to hold the data and then perform bookkeeping to prepare for the next allocation.</u></p>

><p><u>Accessing data in the heap is generally slower than accessing data on the stack because you have to follow a pointer to get there. Contemporary processors are faster if they jump around less in memory. A processor can usually do its job better if it works on data that’s close to other data (as it is on the stack) rather than farther away (as it can be on the heap).</u></p>

><p><u>When your code calls a function, the values passed into the function (including, potentially, pointers to data on the heap) and the function’s local variables get pushed onto the stack. When the function is over, those values get popped off the stack.</u></p>
>   <div style={{ display: 'flex', marginTop: '0.5rem', color: '#009B77' }}>
>     <span>↘</span>
>     <div>
>      <p>The exact same principle actually applies to the all scopes examined in section 3.2. As an inner scope terminates, its local variables are popped from the stack and destroyed. It's all starting to make more sense now, isn't it? Note, however, that <u>the underlying heap data is not blindly deallocated</u>. <u>Rust's memory model dictates that heap memory is tied exclusively to ownership; therefore, the data is only dropped if the variable going out of scope was the owner, rather than just a borrowed reference</u>.</p>
>     </div>
>   </div>

>Keeping track of what parts of code are using what data on the heap, minimizing the amount of duplicate data on the heap, and cleaning up unused data on the heap so that you don’t run out of space are all problems that ownership addresses. Once you understand ownership, you won’t need to think about the stack and the heap very often. But knowing that the main purpose of ownership is to manage heap data can help explain why it works the way it does.
</Callout>

## Ownership Rules

>First, let’s take a look at the ownership rules.

>- Each value in Rust has an **owner**.<br />
>   <div style={{ display: 'flex', gap: '8px', marginTop: '0.5rem', color: '#009B77' }}>
>     <span>↳</span>
>     <div>
>       While this fact is true, it can cause confusion if we do not immediately distinguish between variables of types that implement the `Copy` trait and those that do not. Generally speaking, the fact that every value has an owner is fairly obvious: from a programmer's perspective, practically every value must be bound to a variable (its owner), otherwise, that specific value would be unusable. However, starting to view the concept of ownership as counter-intuitive for every variable is, in my opinion, incorrect and leads to confusion due to how the `Copy` trait works. As noted in section 3.2, one major mechanism you truly need to worry about is <u>the `=` assignment for variables whose types do not implement `Copy`</u>. For example, the variable <u>on the RIGHT side of the equals sign</u> (specifically, the memory address it points to) is <u>moved</u> if we do not apply the `&` symbol to explicitly <u>copy</u> its address. When this happens, it permanently <u>loses ownership of both its stack data (the memory address pointing to the heap and some metadata) and the underlying heap memory itself</u>. In these specific cases, <u>the LEFT variable gains ownership of the heap memory address + metadata and the data it points to</u>. Once the LEFT variable is destroyed at the end of the scope in which it is defined, ownership is permanently lost and the data is destroyed (both the stack-bound heap address + metadata, and the heap data itself). In any case, the <u>EXISTING data will always have an owner</u>. With this fundamental point clarified, it is important to note that <u>the ownership mechanism becomes more nuanced when the `=` assignment is combined with the reference operator (`&`)</u>. The following rule analyzes exactly what happens in this scenario in greater detail.
>     </div>
>   </div>
>- There can only be <u>one</u> owner at a time.<br />
>   <div style={{ display: 'flex', gap: '8px', marginTop: '0.5rem', color: '#009B77' }}>
>     <span>↳</span>
>     <div>
>       This concept aligns seamlessly with our previous observations and does not conflict with the underlying mechanics of types implementing the `Copy` trait. When a value belonging to one variable is copied to another, there must necessarily exist <u>TWO distinct copies of that value in memory, bound to TWO distinct variables (the owners)</u>. However, <u>this principle becomes more complex when the assigned value is a memory address (a reference)</u>. As we saw in section 3.2, the variable on the LEFT side of the assignment receives a COPY of the address of the RIGHT side variable, taking ownership of the COPY of the pointer (address) itself. The subtle but critical detail here is that <u>the underlying data the address points to is still owned by the original variable, which maintains full ownership over that data</u>. <u>The RIGHT side variable maintains full ownership of its own copy of the address as well</u> (this one is quite obvious). This means <u>you can use your copied reference to access the data, but when the original owner is dropped from memory, the underlying data is deallocated</u>. <u>At that point, the secondary reference becomes invalid, and the compiler will stop you from accessing it!</u> This is a crucial concept not previously observed in section 3.2, perfectly illustrated by Code 4.1.1 and Code 4.1.2 below. Furthermore, the restriction that a value may have only a single owner at any given time does not preclude the possibility of data losing its ownership entirely and being deallocated.
>     </div>
>   </div>
>- When the owner goes out of scope, the value will be dropped.<br />
>   <div style={{ display: 'flex', gap: '8px', marginTop: '0.5rem', color: '#009B77' }}>
>     <span>↳</span>
>     <div>
>       This absolute rule directly reflects our observations from section 3.2 and needs no further breakdown.
>     </div>
>   </div>

## Ownership Mechanics for References

As mentioned above, ownership mechanics for the scalar types discussed in section 3.3 are rather trivial. However, they can be intentionally made more complex if one chooses to <u>copy the stack address where these typed variables are stored</u> (i.e., by taking a reference). In such scenarios, the exact same logic applies as when copying the address of a `String` variable (some crucial and related concepts are highlighted in the yellow-box of section 3.2), since <u>the address of a `String` typed variable is also stored on the stack</u>. Ultimately, in both cases—whether dealing with types that implement the `Copy` trait or those that do not—<u>copying an address creates a situation where the left-side variable takes ownership of the address itself, but not the underlying value it points to, regardless of whether that data resides on the stack or the heap</u> (Code 4.1.1 and Code 4.1.2 clear up this mystery once and for all).

One might therefore wonder why the compiler's behavior differs between types that do not implement the `Copy` trait and those that do, in cases where the variable itself is assigned rather than its address. The answer is that the compiler is smart enough to know that, for scalar types, it is simply not worth the effort to move the ownership (invalidating the RIGHT side variable) instead of generate two distinct copies of data having two distinct owners. This is because copying the actual data is so cheap that it generates no meaningful computational or spatial overhead.

These recent examples might cause some confusion. If so, it is highly recommended to review the concepts from section 3.2 and carefully compare them with this section to clear up any doubts. Although these scenarios would cause complex <u>runtime</u> errors in other languages, the Rust compiler is specifically designed to catch and flag them before deployment—right at <u>compile time</u>. In fact, <u>compiler errors should never be viewed as flaws in the language, but rather as its greatest strength</u>. They force you to resolve complex issues at the right moment, preventing catastrophic bugs in production!

The language itself makes it difficult for these issues to occur in the first place. For instance, once you understand Code 4.1.1, preventing the issue is simple: <u>just remember not to return a reference to a variable created in an inner scope back to the outer scope (functions follow this exact same logic, as seen in section 3.2)</u>. Similarly, preventing the error in Code 4.1.2 is simply a matter of remembering <u>not to move types that do not implement the `Copy` trait into an inner scope (if an outer-scope-usage is required)</u>. <u>The resolution strategies observed in section 3.2 should never be forgotten</u>; they are excellent programming patterns for avoiding complex errors like these.

<Callout icon="key" color="#12A0D7" iconType="regular">
In fact, a standard programming pattern in Rust is to <u>define your core, non-temporary variables</u> (your main application state) <u>within the `main` function</u>, often <u>instantiating them from specific imported modules</u>. <u>If these variables need to be modified, you do so by passing them to functions. Within those function scopes, local variables (parameters) temporarily borrow the original data to read or mutate it safely.</u>
</Callout>

Regarding Code 4.1.1, a beginner might mistakenly assume that avoiding returning references from an inner scope is the ultimate solution. As we will see later, however, <u>returning references from inner scopes is entirely possible</u>! To allow this, Rust simply requires additional information to guarantee that the reference will not point to data that gets dropped at the end of the inner scope—or anytime before the reference's binding in the inner scope (this means that particular referenced variables will need to be initialized in some outer scope). Specifically, this information (which introduces the concept of **lifetimes**) is tied directly to function constructs rather than raw scopes. This makes sense because, as noted in section 3.2, <u>you will never use raw scopes instead of functions, except for the rapid deallocation of temporary variables</u>.

Despite this, it is also possible to return references from a bare scope. However, the rules governing this specific use case differ from those applied to functions. In fact, a bare scope can be thought of as the normal flow of instructions—as if the program didn't explicitly use one—with the only difference being the subsequent deallocation of memory allocated within it at its end. The compiler's rules follow this exact logic, meaning it will not be necessary to specify any explicit lifetimes.

Code 4.1.3 and E-Output 4.1.3 demonstrate how it is possible to return a reference from an inner scope. You do not need to fully understand the syntax just yet; the key takeaway is that the expression `(heap_ptr as *const u8).add(2)` returns a reference (a memory address pointing to the character `1` on the heap). This works perfectly because the variable `s` outlives the inner scope, ensuring its data remains alive and valid.

<CodeGroup>
```rust Code 4.1.3
fn main() {
    let s = String::from("561");
    
    let addr_of_one = {
        let fat_ptr = &s as *const String as *const usize;
        let heap_ptr = unsafe { *(fat_ptr.add(1)) };
        
        // println!("0x{:016x}", heap_ptr);
        
        unsafe { (heap_ptr as *const u8).add(2) }
        
        /* We are returning a reference pointing to data that will not be 
           deallocated once this scope ends. This works because `s` is 
           defined in the outer scope and is not moved (the reference 
           itself is simply copied)! */
    };
    
    let one = unsafe { *addr_of_one };
    
    println!("Z56{}", one as char);
}
```

### Clarifying the 'Borrowing' Terminology

At this point, we can finally conclude this section by recalling Rust's official terminology regarding the use of references.

>We call the action of creating a reference <u>borrowing</u>. As in real life, if a person owns something, you can borrow it from them. When you’re done, you have to give it back. You don’t own it.

Whenever a reference to a variable exists, Rust will indicate potential compilation errors using the term 'borrowing'. This section comprehensively clarifies the reasoning behind this naming convention. The variable on the LEFT side of an `=` assignment (where the `&` operator appears on the RIGHT) essentially <u>borrows the value pointed to by the address</u>. Crucially, remember that <u>the left-side variable takes ownership of the pointer itself because the memory address is copied</u> (meaning two distinct instances of the address now exist in memory). Indeed, <u>Code 4.1.2 would compile perfectly</u> if the final `println!` statement—which attempts to access the deallocated memory through the `s2` pointer—<u>did not exist</u>. This is because <u>`s2` owns its own pointer</u>; as long as the program does not actually try to read the freed data, no rules are broken, and the compiler allows the code to pass.
