From this point forward, several topics have been omitted either because they were already analyzed in detail in section 3.2 or in the previous one, or because they were deemed superfluous. Nevertheless, it is worth mentioning one concept that is perhaps less marginal:

>When a variable goes out of scope, Rust calls a special function for us. This function is called `drop`. Rust calls `drop` automatically at the closing curly bracket.

The following section, however, has been preserved—though heavily modified—and directly integrated with our raw memory analysis. Even though it revisits the same reasoning found in section 3.2 and 4.1, it offers a more visual and less abstract perspective on memory addresses and data, while also providing a few details not yet covered.

<ol className="list-comments">
 <li>
 The statement `let mut s1 = String::with_capacity(10)` declares `s1` as a mutable `String` with an explicitly defined `capacity` of `10`. We do this to ensure absolute certainty about the memory fields we are going to access. If the `capacity` and the `len` (length) were identical, distinguishing between the two values in raw memory would require overly complex techniques.
 </li>
 <li>
 `s1.push_str("hello")` appends the string `hello` to `s1`. At this point, `s1`'s internal data perfectly matches what is shown in Figure 4.2.1, with the sole exception of the `capacity`. Note that if we hadn't declared `s1` as mutable, modifying it after creation would have been impossible!
 </li>
 <li>
 The complexity of the statement `let ptr = &s1 as *const String as *const usize` lies entirely on the right side of the `=` sign, as the left side simply declares an immutable variable named `ptr`.

The expression `&s1 as *const String as *const usize` starts by retrieving `s1`'s memory address on the STACK. It is important to remember that <u>`s1` is not merely the string data residing on the HEAP</u>, as shown in Figure 4.2.1. In fact, the address obtained by `&s1` points to the very first piece of data in memory belonging to the LEFT-hand structure depicted in Figure 4.2.1. In reality, under the Rust compiler's actual memory management, the data layout is not ordered exactly as shown in Figure 4.2.1. In fact, as Code 4.2.1 demonstrates, the first value residing in memory at `s1`'s address is the `capacity`'s one, not the pointer to the string data on the HEAP! Uncovering this specific structural quirk actually took quite a bit of effort.

Returning to the line of code in question: once we obtain the address of `s1`'s STACK data structure, `as *const String` acts as an explicit **type cast**. It allows us to treat `&s1` as a raw pointer to a `String` data structure (which is exactly what it represents). <u>This initial step is required before we can perform the second</u> cast, `as *const usize`. This final cast is necessary so we can operate on it as a <u>generic raw pointer</u>.
 </li>
 <li>
 The `unsafe { ... }` block encompassing almost all of Code 4.2.1 is strictly necessary to operate directly at the raw memory level, preventing the Rust compiler from stepping in and stopping us <u>for safety reasons</u>! Generally, <u>using `unsafe` is discouraged unless absolutely required</u>. However, this is one of those exceptions: to explore what truly happens under the hood and manipulate memory addresses, we have to tell the compiler that we know what we're doing, by reassuring it with an `unsafe` block. Don't worry, though! Later on, we will see exactly how to analyze low-level memory using a completely safe approach.

There is one more caveat to add. In idiomatic Rust, `unsafe` should be scoped as narrowly as possible; writing massive `unsafe` blocks like the one in Code 4.2.1 is generally considered bad practice (we will explain exactly why in Ch. 20). In this specific instance, it is structured this way simply because literally almost every single line of code inside that block performs an unsafe operation 😂.
 </li>
 <li>
 The line `let capacity = *ptr` defines the `capacity` variable by **dereferencing** the generic raw pointer `ptr` that we defined in `#3`!
 
 <u>The dereference operator (`*`) allows you to access the value stored in memory at a specific address.</u> In this case, the pointer `ptr` holds the memory address that—as noted earlier—points to the string's `capacity` field. This means that <u>the expression `*ptr` evaluates to `10`</u>, and this value is bound to `capacity` via `let`.

 <u>Dereferencing is the exact inverse of referencing (`&`).</u> In fact, writing `*&ptr` is functionally identical to simply writing `ptr`; a rule that holds true for any data type.

 Dereferencing a <u>raw pointer</u> is an unsafe operation! Attempting to write `*ptr` outside of an `unsafe` block will trigger a compiler error.

 That being said, dereferencing a standard reference (`&`)—rather than a raw pointer—is a perfectly safe operation in Rust! For example, Code 4.2.2 compiles and runs smoothly.

 ```rust Code 4.2.2
 fn main() {
     let x = 17;
     let y = &x; // 'y' is a standard, safe reference to 'x'.

     // We can safely dereference 'y' using '*' without an 'unsafe' block!
     let z = *y; 

     println!("{z}"); // Prints: '17'.
 }
 ```
 
 At this point, a natural question arises:
 
- <span style={{ color: "#964B00" }}><b>Q</b>: Why is dereferencing a standard reference considered safe, while dereferencing a raw pointer is considered dangerous?</span><br />
- <span style={{ color: "#008080" }}><b>A</b>: The answer primarily lies in the different <u>operations</u> permitted on a raw pointer versus a standard reference. As we are going to see in `#6`, and as clearly demonstrated in Code 4.2.1, <u>you can perform pointer arithmetic on a raw pointer</u>. <u>When you subsequently dereference that shifted pointer, you can access memory areas that might be completely unallocated or belong to entirely different variables. If not handled with extreme care, this capability can trigger severe vulnerabilities and undefined behavior—things Rust traditionally works very hard to prevent.</u></span><br />

  <span style={{ color: "#008080" }}>Despite these risks, Rust provides the `unsafe` keyword to guarantee maximum flexibility for low-level scenarios that require it, trusting the programmer only when they are absolutely certain of what they are doing.</span><br />

  <span style={{ color: "#008080" }}>The story is completely different for standard references created with the `&` operator. First and foremost, <u>you cannot perform pointer arithmetic on a standard reference</u>! <u>This single restriction prevents you from accessing memory outside the strict control of the compiler.</u> Because you cannot mathematically alter the address, it logically follows that:</span><br />

  - <span style={{ color: "#008080" }}>A reference can only point to existing, valid variables (meaning data that has not been dropped at the end of an inner scope).</span><br />
  - <span style={{ color: "#008080" }}><u>You simply cannot use one variable's reference to magically peek into memory belonging to another!</u></span><br />

  <span style={{ color: "#008080" }}>The ownership mechanisms we observed in the previous section naturally <u>prevent access to freed or unowned memory</u>, eliminating vulnerabilities and unexpected behavior. This is exactly why Rust correctly identifies standard references (`&`) as risk-free and inherently safe.</span><br />

  <span style={{ color: "#008080" }}>However, as we will explore later, <u>allowing multiple variables to hold references pointing to the exact same memory location can create complex scenarios that require detailed analysis.</u></span>
 </li>
 <li>
 The statement `let ptr_to_heap = *(ptr.add(1))` works much like the previous line. The key difference is that before accessing the value via `*`, we use `.add(1)` to shift the memory address held in `ptr`. This allows us to access the specific STACK address that points directly to the HEAP data containing our `hello` string. This process serves as a perfect example of the unsafe operation (pointer arithmetic) we discussed earlier. Thinking back to step `#4`, a quick glance at Code 4.2.1 reveals that it is packed with pointer arithmetic. This is exactly why the entire snippet had to be wrapped in a single, massive `unsafe` block.

 At this point, we must highlight a few fundamental details:

 - It is important to remember that while <u>a single memory address technically points to one byte (8 bits) of data</u>, <u>the `.add(1)` operation uses pointer arithmetic</u>. <u>Since we are operating on a `*const usize` pointer, adding 1 moves the pointer forward by the size of one complete `usize` (usually 8 bytes)</u>, properly aligning us with the next chunk of data in the `s1` structure on the STACK. If you look closely at E-Output 4.2.1, you will notice that `0x7ffe70bccbb8` (the address of the `ptr_to_heap` field) is located exactly 8 bytes after `0x7ffe70bccbb0` (the address of the `capacity` field).

   ```math
   \mathtt{7ffe70bccbb0 + 8 = 7ffe70bccbb8}
   ```

   These 8 bytes—or 64 bits—perfectly match the size of a `usize`, which corresponds to a single CPU register on a 64-bit architecture. Seeing these specific values printed shortly after in E-Output 4.2.1 practically proves the pointer arithmetic concepts we just discussed.

 - The previous point also explains the quirks we observed in step `#3`: when applying the `.add(x)` method to a `*const String` pointer, the address actually shifts by `24 * x` bytes. This is because <u>the compiler automatically multiplies the addition by the size of the referenced type</u>. In this case, <u>a `String` structure (Figure 4.2.1) occupies 24 bytes (comprising three 8-byte fields: a heap pointer, length, and capacity)</u>. This is exactly why we performed an additional cast to `*const usize` instead of keeping `*const String` as the raw pointer type in `#3`!

 - You can visually verify each address is indeed 8-byte size by looking at a memory address format, such as `0x7ffe70bccbb0`. <u>While it looks like 12 characters (excluding the `0x` hexadecimal prefix), the true underlying 64-bit value is `00007ffe70bccbb0`. When you count those digits, you get exactly 16 hexadecimal characters. Because each hex digit is 4 bits, 16 digits yield 64 bits, which is exactly 8 bytes per field.</u>

   ```math
   \mathtt{\underbrace{\underbrace{\underbrace{\underbrace{0}_{4}\underbrace{0}_{4}\underbrace{0}_{4}\underbrace{0}_{4}}_{16}\underbrace{\underbrace{7}_{4}\underbrace{f}_{4}\underbrace{f}_{4}\underbrace{e}_{4}}_{16}}_{32}\underbrace{\underbrace{\underbrace{7}_{4}\underbrace{0}_{4}\underbrace{b}_{4}\underbrace{c}_{4}}_{16}\underbrace{\underbrace{c}_{4}\underbrace{b}_{4}\underbrace{b}_{4}\underbrace{0}_{4}}_{16}}_{32}}_{64 \text{ bits} = 8 \text{ bytes}}}
    ```
 </li>
 <li>
 The line `println!("[Address of capacity (on the STACK)]: {:p}", &capacity)` simply prints the stack memory address of the `capacity` variable. To achieve this, we must use the `:p` **format specifier**, which instructs the `println!` macro to format the output as a memory address (a pointer). This step is crucial for two main reasons:
 
 - First, it allows us to directly observe the address, which—alongside the addresses of `ptr_to_heap` and `len`—made our pointer arithmetic analysis in `#6` possible.

 - The second reason is tied to the numerical structure of stack addresses themselves. If you compare them, you will notice that <u>stack addresses are numerically much higher than heap addresses</u>. This is no coincidence; it is a direct consequence of how memory is structured at a low level by the operating system.
   
   ```math
   \mathtt{140730789841840 = 7ffe70bccbb0 \gg 564f58e4cd60 = 94898793794912}
   ```
   ```math
   \downarrow
   ```
   ```math
   140730789841840 - 94898793794912 = 4,583199605 \cdot 10^{13}
   ```

In contrast, the heap starts near lower memory addresses and grows upward (towards higher addresses, except when dynamically filling memory gaps).</u>

   For this reason, our earlier statement in `#3`—'the first value residing in memory at `s1`’s address is the `capacity`’s one'—might seem debatable. Because `capacity` sits at the lowest memory address compared to `ptr_to_heap` and `len`, it was physically the last field pushed onto the stack.

   While this is true regarding allocation order, <u>memory blocks are traditionally read from the lowest address upward</u>. Therefore, <u>the last item pushed onto the downward-growing stack logically becomes the 'first' item encountered when reading that memory block</u>. It is no coincidence that the base pointer `ptr` points exactly to `capacity`!
 </li>
 <li>
 This marker was added simply to highlight the use of the `print!` macro instead of `println!`. The only difference between the two is that `print!` does not append a newline character after printing the text.
 </li>
 <li>
 The `print_type(&capacity)` function was used primarily for clarity, simply to verify that the type of `capacity` is indeed `usize`. This is a direct result of how `capacity` (along with `ptr_to_heap` and `len`) was initialized: it was assigned the value of `*ptr`. <u>Because `ptr` is defined as a `*const usize` pointer, dereferencing it natively yields a `usize` value.</u>
 </li>
 <li>
 The `println!("[...]:\n{:p}", ptr_to_heap as *const usize)` macro prints the value of `ptr_to_heap` to the terminal. Because `ptr_to_heap` represents a memory address on the heap (specifically, the one pointing to the first character of `hello`, which is `h`), we can use the `:p` format specifier. To achieve this, we can explicitly cast the value from its current `usize` type into a `*const usize` pointer.
 </li>
 <li>
 At this point, we finally trigger the printing of the values stored on the stack for `len` (`5`) and `capacity` (`10`).
 </li>
 <li>
 The line `println!("[Address of 'h' (on the HEAP)]: {:p}", ptr_to_heap as *const u8)` works exactly like the one we analyzed in `#10`. In fact, they are entirely equivalent and print the exact same value (see E-Output 4.2.1).

 The only difference from `#10` is that the pointer is now cast to the `*const u8` type. At this exact moment, the difference isn't visible in the `println!` output because we haven't performed any pointer arithmetic on `ptr_to_heap`. <u>In the following instructions, however, we will do exactly that. Because `*const u8` is a raw pointer pointing to a `u8` (an 8-bit unsigned integer), adding `x` via the `.add(x)` method will shift the pointer in memory by exactly `x` byte at a time</u> (as you can verify in E-Output 4.2.1).

 This brings us back to section 3.3 and our discussion about the `char` type. As explained there, a standalone `char` in Rust always occupies 4 bytes. Because of this, you might mistakenly assume that each character in our string sits 4 memory addresses apart.

 What actually happens is that characters inside Rust strings are stored using UTF-8 encoding. UTF-8 preserves backward compatibility with standard ASCII for traditional keyboard characters. Since ASCII encoding allocates just a single byte for each alphanumeric character, <u>every letter in `hello` takes up exactly 1 byte on the heap</u>. Later on, we will explore the more complex scenarios of UTF-8, where characters can occupy anywhere from 1 to 4 bytes in ways that might seem unpredictable at first glance.
 </li>
 <li>
 `println!("['h' raw byte] = {}, parsed as char: {}", *(ptr_to_heap as *const u8), *(ptr_to_heap as *const u8) as char)` simply performs two actions:

 - It accesses the value pointed to by `ptr_to_heap` using the dereference operator (`*`). Because the pointer type is explicitly cast to `*const u8`, dereferencing it yields a `u8` value. This explains why E-Output 4.2.1 displays decimal numbers that might initially seem meaningless—they are actually the numeric ASCII codes for those characters (e.g., `104` for `h`).

 - It performs the exact same dereferencing operation, but before printing, it casts the resulting `u8` value into a `char`. This behavior is perfectly valid—and allowed by the compiler without throwing an error—because every possible `u8` value maps directly to a valid Unicode character. However, you still need to know what you are doing to avoid printing meaningless characters!
 </li>
</ol>

## Analyzing Memory - Move Behavior

Let us now (re-)consider (we've already analyzed this behavior in depth in section 3.2 and 4.1) Code 4.2.3, where the address of `s1` is implicitly moved into `s2`.

<CodeGroup>
```rust Code 4.2.3
fn main() {
    let s1 = String::from("hello");

    let ptr1 = &s1 as *const String as *const usize;

    unsafe {
        println!("Capacity = {}, address: {:p}", *ptr1, ptr1);
        println!("'hello' address (HEAP): 0x{:x}=|", *(ptr1.add(1)));
        /* The 0x{:x} syntax allows a usize to be represented as a memory address
           by formatting it in hexadecimal ({:x}). */
        println!("Len = {}, address: {:p}       |", *(ptr1.add(2)), ptr1.add(2));
    }

    let s2 = s1; // Move occurs.

    let ptr2 = &s2 as *const String as *const usize;
    
    println!("                                       |");

    unsafe {
        println!("Capacity = {}, address: {:p}  |", *ptr2, ptr2);
        println!("'hello' address (HEAP): 0x{:x}=|", *(ptr2.add(1)));
        println!("Len = {}, address: {:p}", *(ptr2.add(2)), ptr2.add(2));
    }
    
    // println!("{s1}"); // error[E0382]: borrow of moved value: `s1`
}
```

Even in that scenario, <u>`s1` is never actually dropped</u>; because it resides in the outer scope in an invalidated state, <u>the compiler knows it no longer owns any data</u> and safely skips its destructor.

## Analyzing Memory - References and Borrowing

Let us now (re-)consider Code 4.2.4. This scenario was also analyzed previously in section 3.2 and 4.1. Here, <u>the memory address of `s1` (in the STACK) is explicitly assigned to `s`</u>. <u>This seamless interaction happens due to Rust's type inference and auto-dereferencing</u>. Because the compiler implicitly assigns `s` the type of a string reference (`&String`), it treats `s` as a direct pathway to the original string. <u>When `s` is used, the compiler automatically follows the reference in memory and handles data as a `String` type</u>. As a result, `s` doesn't need to physically 'inherit' the fields; it simply accesses `s1`'s metadata (`capacity` and `len`) and heap data (`hello`) directly, functioning exactly as if it were the original string. Nevertheless, <u>`s` is not an exact copy of `s1`</u>. This is because <u>the value stored in `s` is a COPY of `s1`'s memory address (specifically, the `capacity`'s address), rather than the actual data contained within `s1`</u>! Since the two copies of the address must exist in two distinct memory locations, writing `&s1` and `&s` yields two distinct results. Specifically, `&s1` (the memory address of `s1`) is exactly the memory address of its `capacity` component, whereas `&s` is a completely separate memory address that contains a pointer to `s1` (meaning it holds the value `&s1`).

As you can clearly see, the double-free memory error has disappeared, allowing the code to terminate gracefully without crashing the program! This specific fix provides the perfect clue to understanding the true purpose of the `capacity` field. In fact, it is a field used by Rust's allocator to <u>deallocate the memory of its associated string</u>.

When a `String` goes out of scope, Rust automatically calls its `drop` implementation to clean up the memory. <u>The deallocator looks at the `capacity` field to determine exactly how many bytes need to be freed. By manually forcing the `capacity` to `0` in our experiment, we effectively tricked the deallocator: when it checked how much heap memory to clean up, it saw 0 and therefore did nothing.</u> By skipping the deallocation step, the heap memory was left untouched, successfully preventing the double-free error when the second variable went out of scope.

<u>Rust's ownership mechanism is expressly designed to prevent double (or triple, etc.) free memory errors, dangling pointers, and unsafe programming patterns.</u> The language's architects have truly thought of everything. Furthermore, <u>writing idiomatic Rust is significantly simpler</u>. For instance, the earlier section demonstrating assignment (`=`) via the `&` reference showcases a native language feature officially known as <u>borrowing</u>. By utilizing borrowing, the complex workaround seen in Code 4.2.5 becomes completely obsolete. It is far safer and more efficient to pass a temporary reference to `s1` to modify its content within a function, rather than manually forging a second `String` struct to unsafely share the same heap data!

An attentive reader might also have noticed that the memory addresses change at each execution of the code. This behavior is due to the ASLR (Address Space Layout Randomization) system, which randomizes the allocation space of each process for security reasons that will not be analyzed here (as they are quite complex to understand and involve advanced operating system protections).
