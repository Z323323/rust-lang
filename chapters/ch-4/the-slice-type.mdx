**Slices** are an intricate subject in Rust, and for this reason, they were left as the concluding section of Ch. 4. By now, you should possess the theoretical foundation required to understand their underlying mechanics. To start, let's look at the definition provided by the official book.

>Slices let you reference a contiguous sequence of elements in a **collection**. A slice is a kind of reference, so it does not have ownership.

<Note>
The adjective 'contiguous' alone provides a vital clue for understanding heap allocation. The fact that <u>slices can be used on any collection</u>—which <u>often point to data stored on the heap</u>—reveals a fundamental rule: even on the heap, <u>the data belonging to a single collection must be allocated in one contiguous block</u>. However, this strict contiguity per variable does not prevent memory reuse; if deallocations create 'holes' or fragmentation in the heap, Rust's underlying memory allocator will attempt to backfill these gaps with new allocations whenever the space permits.
</Note>

Beneath the surface, <u>slices are essentially pointers bundled with length metadata</u>.

As the official book clarifies, this metadata allows these pointers to safely reference <u>sequences</u> of elements within any typed collection. This is a crucial concept to grasp: <u>the primary purpose of a slice is to reference a continuous sequence, not a single element</u>. <u>Accessing an isolated element—even one located deep within a collection—can already be achieved safely (without `unsafe` blocks) using standard references.</u>

This is demonstrated in Code 4.3.1 below. In this example, we analyze `slice_to_u8_array`, which references a contiguous block of data within the `a` array, alongside `safe_ptr_to_u8_array`, which is a standard reference to a single, <u>arbitrary</u> element inside the same array. Ultimately, Code 4.3.1 illustrates exactly what slices are and how they differ from standard (safe) pointers.

<CodeGroup>
```rust Code 4.3.1 focus={5-42}
fn print_type<T>(_: &T) {
    println!("{}", std::any::type_name::<T>());
}

fn main() {
    let a = [17_u8; 3];
    let ptr = &a as *const u8;

    println!("'a': {:?}", a);
    println!("'a' address on the STACK: {:p}", &a);
    unsafe {
        println!("'a' address on the STACK + 2: {:p}", ptr.add(2));
    }
    println!("'a' length: {}", a.len());

    let safe_ptr_to_u8_array = &a[2];
    print_type(&safe_ptr_to_u8_array); // &u8

    println!(
        "'safe_ptr_to_u8_array' pointer (points to the STACK's 'a' address + 2): {:p}",
        safe_ptr_to_u8_array
    );
    println!("'safe_ptr_to_u8_array' pointed data (on the STACK): {safe_ptr_to_u8_array}");
    // println!("'safe_ptr_to_u8_array' length: {}", safe_ptr_to_u8_array.len());

    let slice_to_u8_array = &a[0..=1];
    print_type(&slice_to_u8_array); // &[u8]

    println!(
        "'slice_to_u8_array' pointed data (on the STACK): {:?}",
        slice_to_u8_array
    );
    println!(
        "'slice_to_u8_array' address (on the STACK): {:p}",
        &slice_to_u8_array
    );
    println!(
        "Address (on the STACK) of the first element pointed by 'slice_to_u8_array' (it's the 'a' address on the STACK!) + metadata: {:p}",
        slice_to_u8_array
    );
    println!("'slice_to_u8_array' length: {}", slice_to_u8_array.len());
}
```

<p><u>The length `metadata` dictates the exact number of bytes to consider when the slice is accessed.</u></p>

By uncommenting the line `println!("{}", safe_ptr_to_u8_array.len())` and attempting to run the code, we can observe a <u>compilation error</u>. This error clearly demonstrates the fundamental difference between slices and standard pointers: the `metadata` field tracking the length of a slice simply does not exist on a standard pointer! This happens trivially because standard pointers and slices are two <u>distinct</u> sides of the same coin.

Regarding this point, pay close attention to the types of `slice_to_u8_array` and `safe_ptr_to_u8_array`. <u>The former is `&[u8]`</u>, while the latter is `&u8`. <u>Square brackets are a universal feature for all slices that point to collections other than strings!</u>

<p><u>Whether you are dealing with primitive numbers, standard library structs, or your own custom types, the slice type is simply the target type enclosed in square brackets:</u></p>

- Primitives: `&[i8]`, ..., `&[u8]`, ..., `&[f32]`, `&[f64]`, `&[bool]`, `&[char]`.
- Standard Library Types: `&[String]`, `&[Option<i32>]`, ... .
- Your Custom Types: `&[MyStruct]`, `&[User]`.

<p><u>However, there is one notable exception: the specific type used for `String` slices is called `&str`—a clear abbreviation for 'string'.</u></p>

One might wonder what the difference is between `&[char]` and `&str`. The answer is that a `&[char]` references a contiguous block of memory where <u>every single element is strictly 4 bytes wide</u>, while `&str`, on the other hand, references <u>data encoded in UTF-8</u>. UTF-8 is a variable-length encoding, meaning <u>different characters take up different amounts of memory</u>.

The next paragraphs will analyze string slices in detail, explaining why the `&str` type <u>must be handled carefully</u> and differs slightly from other slice types, beyond just the absence of square brackets in its name.

At this point, it is crucial to clarify a fundamental concept. <u>The `[]` operator essentially allows us to perform pointer arithmetic on safe references (obtained via the `&` operator).</u> Given what we observed in section 4.2, a natural question arises:

- <span style={{ color: "#964B00" }}><b>Q1</b>: If the very purpose of `unsafe` blocks is to restrict pointer arithmetic, why is it permitted on safe references? After all, one could theoretically still jump into unsafe memory regions using pointer math.</span><br />
- <span style={{ color: "#008080" }}><b>A1</b>: In reality, this is precisely what makes the `[]` operator safe: unlike raw arithmetic on raw pointers, it performs additional validations (bounds checking) on the memory regions being accessed. For instance, attempting to access an element outside the bounds of array a will trigger a runtime error rather than a compilation error, as we saw in section 3.3. Thus, the language guarantees the safety of any pointer operations conducted through the `[]` operator.</span>

You might not have noticed this detail in Code 4.3.1, but <u>we performed a memory analysis almost entirely without using `unsafe` blocks</u>! This was possible thanks to safe references, the features of the `println!` macro, and the `[]` operator.

Let us now focus on the second statement from the official book: 'A slice is a kind of reference, so it does not have ownership'.

- <span style={{ color: "#964B00" }}><b>Q2</b>: If Rust is fundamentally built on the ownership model, why are slices exempt?</span><br />
- <span style={{ color: "#008080" }}><b>A2</b>: The book points out that this is because slices are a kind of reference. It is true in a broad sense because, as previously analyzed, references and pointers—being simple memory addresses—implement the `Copy` trait. This means <u>assigning one slice to another neither triggers a move of the underlying data, nor invalidates the slice on the RIGHT side of the assignment</u>, because TWO distinct copies of that pointer are simply generated on the stack. However, stating that slices lack ownership is not entirely accurate. In reality, a <u>slice has ownership of its own pointer, but not of the underlying data it points to</u>.</span>

## The Power of Slices: Zero-Cost Memory Access

In the previous section, our primary focus was on the structure of slices compared to standard references. Now, it is important to clarify exactly why they represent a fundamental construct for programming correctly in Rust.

Suppose we want to access and process a substring of a pre-existing string (of type `String`) using a function. If string slices (`&str`) did not exist, we would either have to physically copy the desired substring into a new area of heap memory (the one created inside the function's scope), or manually pair a pointer to the starting address with a separate length variable to let the function know how many bytes to read. Fortunately, this latter approach is exactly what slices do for us: they are simply a pointer bundled with length metadata! <u>This exact same principle applies to any sub-collection within any collection of elements, not just to the characters in a string.</u>

The issue of physically copying sub-collections into new areas of the HEAP, alone, would generate computational overhead and, above all, an immense waste of space. This is especially true considering the same process would have to occur every time we wanted to access a sub-section of any collection—even on the STACK (where it would still cause needless memory duplication and execution delays).

## The Data Flow Pipeline

Recapping what has been discussed thus far: functions (along with 'methods', a specialized variant of functions we will explore later) are the primary mechanism for processing data in Rust. Specifically, <u>the fundamental data required for a program's execution will reside in the `main` function, which utilizes reference passing to interact with other functions</u> for the reasons previously detailed. These references come in two forms: <u>safe single references via `&`, and slices</u>.

When considering a database—the de facto standard for long-term storage—the overall data pipeline operates similarly: <u>data is fetched from the database, initialized in the `main` function, and then processed by passing references or slices down to functions or methods</u>.

### Idiomatic Slice Usage in Functions

It is useful to note that <u>the primary use of slices will involve mutating specific sections (sequences of elements) within collection types</u>. <u>What cannot be achieved through slices, however, is the insertion or removal of elements from these collections.</u> This constraint exists because <u>adding or removing values within a slice</u>—which by definition is just a window into a larger collection—<u>would either fragment the underlying collection's memory or risk overwriting unintended adjacent values</u>. For this reason, <u>any structural changes must be applied directly to the original collection variable itself</u>. <u>Slices are entirely excluded from this capability.</u>

Code 4.3.2 is presented below to clarify the following points:

- The idiomatic use of slices (in this case, `&[u8]`) passed through functions.
- The difference in usage between slices and references, again within the idiomatic context of functions.
- The possibility of leveraging single-element slices as if they were standard references, in order to avoid using the `*` operator.

<CodeGroup>
```rust Code 4.3.2
fn mutate_slice(u8_slice: &mut [u8]) {
    u8_slice[0] = 20;
    u8_slice[1] = 20;
}

fn mutate_ref(u8_ref: &mut u8) {
    *u8_ref = 0;
}

fn mutate_ref_as_a_slice(u8_slice: &mut [u8]) {
    u8_slice[0] = 0;
}

fn main() {
    let mut a = [17_u8; 5]; // [17, 17, 17, 17, 17]

    mutate_slice(&mut a[3..=4]);
    println!("{:?}", a);

    mutate_ref(&mut a[1]);
    println!("{:?}", a);

    mutate_ref_as_a_slice(&mut a[0..=0]);
    println!("{:?}", a);
}
```

## The `&str` Slice Type

Code 4.3.1 demonstrates how simply accessing a substring of a given `String`—using the `&` + `[]` operators—and binding it to a variable—using the `let` keyword—automatically <u>generates a pointer to the heap</u>, without copying any data in memory, bundled with length metadata under the hood. Indeed, <u>`sub_string` is automatically and implicitly stored by the compiler as a string slice (`&str`)</u>. <u>The compiler is able to set this length metadata via `0..=3`: it knows it must create a pointer with a length of 4 bytes.</u>

<CodeGroup>
```rust Code 4.3.3 focus={5-16}
fn print_type<T>(_: &T) {
    println!("{}", std::any::type_name::<T>());
}

fn main() {
    let s = String::from("Some very long string");
       
    let sub_string = &s[0..=3]; // 'Some'
    print_type(&sub_string);
    
    let ptr = &s as *const String as *const usize;
    let sub_str_ptr = sub_string as *const str as *const usize;
    
    unsafe { println!("s data address (on the HEAP): 0x{:x}", *(ptr.add(1))); }
    println!("sub_string pointer to the HEAP: {:p}", sub_str_ptr);
}
```

<u>Attempting to access a single element of a string via the `[]` operator, rather than using a range, is flagged by the compiler as an error.</u> To clarify, the syntax `0..=3` used in Code 4.3.3 literally generates an instance of type `std::ops::RangeInclusive`, just as `0..4` would generate a `std::ops::Range`.

If we had written `let character = &s[0]` in Code 4.3.3, the compiler—instead of assigning the (address of) value '`S`' to `character`—would have produced C-Output 4.3.3.2:

Rust forbids single-element indexing on strings (e.g., `s[0]`), but it absolutely allows range slicing (e.g., `&s[0..4]`).

Although <u>this error could easily be resolved by employing the previous 'trick' and writing `let character = &s[0..=0]`</u>, Code 4.3.1 and Code 4.3.2 clearly demonstrate how <u>accessing a single element of an array of unsigned `u8` integers via `&a[0]` generates no compilation error</u>.

This happens because if you try to write `let c = s[0]` Rust has to make a hard decision about what `[0]` should actually return, and <u>both available options violate core Rust philosophies</u>:

- Option A: <u>Return a byte (`u8`).</u> If `[0]` returns just the first byte, it breaks the programmer's mental model. <u>If a string starts with a 4-byte emoji, getting just the first byte gives you a meaningless fragment of data, not a character.</u>
- Option B: <u>Return a logical character (`char`).</u> If `[0]` is supposed to return the first full character, then what happens when you ask for `s[100]`? <u>Because UTF-8 characters vary from 1 to 4 bytes in length, the compiler cannot simply "jump" to the 100th character. It would have to start at the beginning of the string and read through it, byte by byte, counting characters until it reaches 100.</u>

<p><u>In programming, the `[]` operator comes with a strong universal expectation: it must be a fast, constant-time $O(1)$ operation. If Rust chose Option B, `[]` would secretly be an $O(N)$ operation, hiding a potentially massive performance cost. Rust refuses to hide expensive operations behind innocent-looking syntax. Therefore, it completely forbids single-element indexing on `&str`.</u></p>

While you cannot ask for a single element, you can ask for a chunk of bytes using a range. When you write `&s[0..4]`, you are explicitly telling the compiler: 'Give me a new `&str` pointing to the block of memory <u>from byte index 0 up to byte index 4</u>'.

Because you are explicitly providing the <u>raw byte indices</u>, it remains a blazing fast $O(1)$ operation. The compiler simply creates a new pointer with the starting address you specified and a length of 4.

<p><u>Because you are working with byte indices, you could accidentally slice a multi-byte character right in half, which would result in invalid UTF-8 (corrupted text) and compromise the 'Option A' avoidance we just talked about. In this case, we must find a safe workaround to be able to use slices with strings, and we are therefore forced to follow this path.</u></p>

To prevent the problem we just discussed, <u>the `[]` operator with ranges includes a built-in safety check</u>. <u>At runtime, Rust checks if the indices you provided fall exactly on valid UTF-8 character boundaries:</u>

- If they do, it successfully returns the new `&str`.
- If you accidentally slice through the middle of a character, <u>the program will immediately panic and crash</u> to protect the integrity of the text data. Code 4.3.4 and C-Output 4.3.4 clearly demonstrate this specific issue.

<ol className="list-comments">
 <li>
 The `std::ptr::addr_of!(str_slice)` macro is a tool we have not yet analyzed. The value it returns is <u>a raw pointer to the physical STACK address where the `str_slice` variable itself is stored</u>.
 
 The reason we must use this macro relates to the structural nature of the `str_slice` pointer. If we proceeded as before—defining `ptr` as `str_slice as *const str as *const usize`—we would encounter an unresolvable issue when trying to print the STACK address and the value of the `len` field.

 Specifically, one might logically attempt to write `(&ptr).add(1)` to read the pointer's STACK address and shift it by `1` (which translates to 8 bytes, since `ptr` is `*const usize`) to reach the `len` field.
 
 The problem here lies in how the dot operator (`.`) works: <u>it automatically dereferences a value until it finds a type that implements the requested method</u>. Because `add` is a method belonging to raw pointers, calling `(&ptr).add(1)` causes the compiler to strip away the reference, dereferencing `&ptr` back to the raw `ptr`. Consequently, <u>it applies the 8-byte shift to the HEAP pointer address (the text data starting address itself), rather than the STACK address</u>! By using `std::ptr::addr_of!(str_slice)` instead, <u>we obtain a true raw pointer to the stack memory</u>, allowing us to successfully apply `.add(1)` and reveal the `len` field.
  
 At this point, we should emphasize that a slice (whether it contains a string literal or not) is structurally very different from a standard `String`. Most notably, <u>a slice only 'contains' a `len` field; it lacks a `capacity` field</u>.
 
 Considering our previous analysis of `capacity`, this makes perfect sense. Capacity exists solely to track dynamically allocated heap space for potential deallocation. Because a slice is merely a pointer on the stack (occupying exactly 16 bytes: 8 for the address, 8 for the length), the compiler does not need to read a `capacity` field to deallocate it. The 16 bytes are simply popped off the stack when the scope ends. Furthermore, as noted earlier, destroying a slice does not erase the underlying data it points to.

 One might rightfully ask:
 
 - <span style={{ color: "#964B00" }}><b>Q3</b>: How can we free the string `hehe` from Code 4.3.5 from memory?</span>
 - <span style={{ color: "#008080" }}><b>A3</b>: The ultimate truth is that <u>we cannot</u>. <u>The string `hehe` is not stored on the heap.</u> Instead, <u>it is hardcoded into a distinct memory region known as `.rodata` (Read-Only Data)</u>. <u>This segment is physically baked into the compiled executable binary itself, meaning the data is loaded by the operating system at startup and persists for the entire duration of the program.</u></span>
 </li>
 <li>
 The expression `*ptr as *const u8` is necessary to analyze each byte of the string `hehe` individually, allowing us to perform the `.add(x)` pointer arithmetic intuitively, just as we did before. Had we not cast it to a 1-byte type, calling `.add(1)` would have shifted the address forward by 8 bytes from the starting letter '`h`'. This would have caused the pointer to overshoot the string entirely, resulting in the reading of garbage data in memory that does not belong to `hehe`.
 </li>
</ol>

### `&str` - Usage

In this section, we will analyze `&str` from a more practical perspective, initially following the official book's approach.

To this end, the official text first presents an example using the `String` type to highlight its limitations.

Code 4.3.6 demonstrates the use of a function that takes a string of words separated by spaces and returns the first word it finds in that string. If the function doesn’t find a space in the string, the whole string must be one word, so the entire string should be returned. In particular, <u>by exclusively using the `String` type, Code 4.3.6 is constrained to returning the index of the word</u>, deriving its location from the occurrence of a space character. Later, Code 4.3.7 will show how to overcome this limitation in an idiomatic way through `&str`, allowing the function to return the literal content of the substring rather than a detached index.

Although Code 4.3.6 takes inspiration from the code presented in the official book, note that it has been heavily modified to make more logical sense and avoid introducing inconsistencies.

For example, even though the following code does not follow an idiomatic approach—since it returns the final index of the found word rather than the word itself (within the `first_word` function)—it still allows us to achieve the desired result. To do this, using a slice in the `main` function is mandatory (assuming we want to avoid introducing yet another `unsafe` block).

Furthermore, Code 4.3.6 resolves any logical inconsistencies regarding the string passed as an argument. Specifically, if an empty string `""` is provided, the function halts immediately and returns `None` (a variant of the `Option<T>` type); otherwise, it attempts to analyze the content.

At this point, we must be careful, as <u>a space could appear as the very first character</u>. In that case, since our goal is to 'return the first word before the first space', <u>a leading space must immediately trigger the return of `None`</u>.

The reader is encouraged to try writing a version that finds the first word regardless of leading spaces, recalling the `trim` function from Ch. 2.

If, instead, valid text is present before the first space, <u>returning the space's index minus one (- 1) will tell the main function exactly where to stop reading the word</u>!

One might now think that all edge cases have been covered, but that is not the case. <u>If a string contains a single word with no spaces whatsoever, searching for a space will yield no result!</u> In this scenario, we must return the entire string—which means returning the index corresponding to the string's total length minus one (since indices always start at 0).

Broadly speaking, this is exactly what Code 4.3.6 accomplishes. Building on the previous explanation, E-Output 4.3.6.1 shows the program's output for `s = String::from("hello world")`, E-Output 4.3.6.2 shows the output for `s = String::from("quertyuiop")`, and E-Output 4.3.6.3 demonstrates the result for any `s` that begins with a leading space or is an empty string (`""`).

<CodeGroup>
```rust Code 4.3.6 focus={5-38}
fn print_type<T>(_: &T) {
    println!("{}", std::any::type_name::<T>());
}

fn first_word(s: &String) -> Option<usize> {
    let bytes = s.as_bytes(); // \
                               // #1
    print_type(&bytes); // ------/

    if s.len() == 0 {
```

The statement `s.as_bytes()` returns a `&[u8]` (a slice of 8-bit unsigned integers).

We need this step to iterate over the string as an array of bytes rather than a sequence of UTF-8 characters. <u>Without this conversion, attempting to call `.iter()` directly on the string would fail to compile; Rust intentionally omits a default iterator for strings to force developers to explicitly choose between iterating over raw bytes or Unicode characters (`.chars()`).</u>

Furthermore, this conversion allows us to access individual bytes directly using the `[n]` index operator (where `0 <= n < s.len()`). As we saw previously, this kind of direct integer indexing is strictly forbidden on a standard `&str`.
</li>
<li>
The expression `bytes.iter().enumerate()` allows us to iterate through the collection while simultaneously tracking our position. Specifically, it creates a pipeline that yields both the current index and a reference to the byte at that index.

Because `bytes` is a byte slice (`&[u8]`), calling `.iter()` creates an **iterator** over that slice. <u>An iterator is an object responsible for fetching items from a collection one by one. It is important to note that `.iter()` returns references to the elements (in this case, `&u8`), meaning it only reads the data without taking ownership or modifying it.</u>

While `.iter()` gives us the items, <u>it does not tell us where we are in the collection</u>. This is where `.enumerate()` comes in. <u>It takes the iterator and wraps it (in a tuple), attaching an index to each item.</u>
</li>
<li>
The statement `if item == b' '` compares each item found in the collection against the byte literal `b' '` (which represents the space character as a `u8` integer rather than a standard Unicode `char`). This means every byte of the string is checked to see if it is a space. If there is a match, the `if` block is executed; otherwise, the `for` loop continues to the next iteration.

Searching for an ASCII character like `b' '` using `.as_bytes()` is 100% safe and will not cause issues, thanks to the brilliant design of UTF-8 encoding. In UTF-8 encoding, all standard ASCII characters (like letters, numbers, and the standard space) take exactly 1 byte, and their values range from 0 to 127 (or 0x00 to 0x7F in hexadecimal). When UTF-8 encodes a multi-byte character (like an emoji or an accented letter), it only uses bytes with values from 128 to 255 (0x80 to 0xFF). Because these numeric ranges never overlap, it is mathematically impossible for a part of a multi-byte character to accidentally look like an ASCII space (`b' '`). Therefore, comparing raw bytes is perfectly safe for ASCII targets.

While searching for a standard space with `b' '` is safe, using `.as_bytes()` breaks down in two specific scenarios where `.chars()` must be used instead:

- <u>Searching for non-ASCII characters</u>: If you want to find an accented letter (like `è`) or an emoji, you cannot use `.as_bytes()`. You must iterate over the Unicode scalar values using `.chars()`.
- Handling 'Unicode Whitespace': A standard space (`b' '`) is not the only type of space. Unicode includes non-breaking spaces, tabs, and em-spaces. If your goal is to find any type of whitespace, byte comparison will fail. You must use `.chars()` combined with the `.is_whitespace()` method.

We will see the method `.chars()` in action later on.

## Slices vs &Slices

<p><u>Every single slice type without the '`&`' is a Dynamically Sized Type (DST).</u></p>

To understand DSTs, you first have to understand the Rust compiler's strictest rule regarding the stack: <u>the compiler must know the exact size (in bytes) of every local variable at compile time</u>.

When you compile a function, the compiler calculates exactly how much memory to allocate for that function's stack frame. <u>If it doesn't know the physical size of a variable, it is mathematically impossible for it to build the stack frame.</u>

<p><u>A Dynamically Sized Type (DST) is a type whose size is only known at runtime.</u></p>

If you tell the compiler, 'I have a `[i32]`' (a slice of 32-bit signed integers), the compiler asks, 'How many elements?'.

Because the bare `[i32]` type does not contain a length encoded in its type signature (unlike a fixed array like `[i32; 5]`), the compiler throws its hands up. <u>It strictly forbids you from declaring `let my_slice: [i32] = ...` because it has no idea how much stack space to reserve</u>.

This logic applies universally to every single slice type in the language. <u>The bare types represent the actual contiguous block of memory itself, which is of an unknown length.</u>

This is where the reference operator (`&`) comes to the rescue. In the context of slices, `&` does much more than just <u>borrow</u> data. It acts as a physical bridge between the unknown and the known.

When you apply `&` to a DST, Rust creates a pointer. <u>It takes the starting memory address of the data block and bundles it together with the length metadata field. This creates a neat, fixed-size package—often referred to as a 'fat pointer' (address + length). While the actual address and length values are strictly populated at runtime, the compiler knows the exact size of this package in advance, allowing it to safely allocate space on the stack.</u>

As a result, <u>the `&` symbol and DSTs are almost exclusively used in tandem, practically functioning as a composite type designated as `&[T]`</u>. Yet, as previously established, viewing this strictly as a single intrinsic type is not entirely accurate.
