>To improve our program, we’ll fix four problems that have to do with the program’s structure and how it’s handling potential errors. First, our `main` function now performs two tasks: It parses arguments and reads files. <u>As our program grows, the number of separate tasks the `main` function handles will increase. As a function gains responsibilities, it becomes more difficult to reason about, harder to test, and harder to change without breaking one of its parts. It’s best to separate functionality so that each function is responsible for one task.</u>

>This issue also ties into the second problem: <u>Although `query` and `file_path` are configuration variables to our program, variables like `contents` are used to perform the program’s logic. The longer `main` becomes, the more variables we’ll need to bring into scope; the more variables we have in scope, the harder it will be to keep track of the purpose of each. It’s best to group the configuration variables into one structure to make their purpose clear.</u>

>The third problem is that we’ve used `expect` to print an error message when reading the file fails, but the error message just prints `Should have been able to read the file`. <u>Reading a file can fail in a number of ways: For example, the file could be missing, or we might not have permission to open it. Right now, regardless of the situation, we’d print the same error message for everything, which wouldn’t give the user any information!</u>

>Fourth, we use `expect` to handle an error, and if the user runs our program without specifying enough arguments, they’ll get an index out of bounds error from Rust that doesn’t clearly explain the problem. <u>It would be best if all the error-handling code were in one place so that future maintainers had only one place to consult the code if the error-handling logic needed to change. Having all the error-handling code in one place will also ensure that we’re printing messages that will be meaningful to our end users.</u>

>Let’s address these four problems by refactoring our project.

## Separating Concerns in Binary Projects

>The organizational problem of allocating responsibility for multiple tasks to the `main` function is common to many binary projects. As a result, many Rust programmers find it useful to split up the separate concerns of a binary program when the `main` function starts getting large. This process has the following steps:

>- <p><u>Split your program into a _main.rs_ file and a _lib.rs_ file and move your program’s logic to _lib.rs_.</u></p>
>- As long as your command line parsing logic is small, it can remain in the `main` function.
>- <p><u>When the command line parsing logic starts getting complicated, extract it from the `main` function into other functions or types.</u></p>

>The responsibilities that remain in the `main` function after this process should be limited to the following:

>- <p><u>Calling the command line parsing logic with the argument values.</u></p>
>- <p><u>Setting up any other configuration.</u></p>
>- <p><u>Calling a `run` function in _lib.rs_.</u></p>
>- <p><u>Handling the error if `run` returns an error.</u></p>

>This pattern is about separating concerns: <u>_main.rs_ handles running the program and _lib.rs_ handles all the logic of the task at hand</u>. <u>Because you can’t test the `main` function directly, this structure lets you test all of your program’s logic by moving it out of the `main` function. The code that remains in the `main` function will be small enough to verify its correctness by reading it.</u> Let’s rework our program by following this process.

### Extracting the Argument Parser

>We’ll extract the functionality for parsing arguments into a function that `main` will call. Code 12.3.1 shows the new start of the `main` function that calls a new function `parse_config`, which we’ll define in _src/main.rs_.

```rust Code 12.3.1
fn main() {
    let args: Vec<String> = env::args().collect();

    let (query, file_path) = parse_config(&args);

    // --snip--
}

fn parse_config(args: &[String]) -> (&str, &str) {
    let query = &args[1];
    let file_path = &args[2];

    (query, file_path)
}
```

>We’re still collecting the command line arguments into a vector, but instead of assigning the argument value at index 1 to the variable `query` and the argument value at index 2 to the variable `file_path` within the `main` function, <u>we pass the whole vector to the `parse_config` function</u>. <u>The `parse_config` function then holds the logic that determines which argument goes in which variable and passes the values back to `main`. We still create the `query` and `file_path` variables in `main`, but `main` no longer has the responsibility of determining how the command line arguments and variables correspond.</u>

>This rework may seem like overkill for our small program, but we’re refactoring in small, incremental steps. After making this change, run the program again to verify that the argument parsing still works. It’s good to check your progress often, to help identify the cause of problems when they occur.

### Grouping Configuration Values

>We can take another small step to improve the `parse_config` function further. At the moment, we’re returning a tuple, but then we immediately break that tuple into individual parts again. This is a sign that perhaps we don’t have the right abstraction yet.

>Another indicator that shows there’s room for improvement is the configuration part of `parse_config`, which implies that the two values we return are related and are both part of one configuration value. We’re not currently conveying this meaning in the structure of the data other than by grouping the two values into a tuple; we’ll instead put the two values into one struct and give each of the struct fields a meaningful name. <u>Doing so will make it easier for future maintainers of this code to understand how the different values relate to each other and what their purpose is.</u>

```rust Code 12.3.2
use std::env;
use std::fs;

fn main() {
    let config = parse_config(env::args().collect::<Vec<String>>());

    println!("Searching for {}", config.query);
    println!("In file {}", config.file_path);

    let contents = fs::read_to_string(config.file_path)
        .expect("Should have been able to read the file");

    println!("With text:\n{contents}");
}

struct Config {
    query: String,
    file_path: String,
}

fn parse_config(args: Vec<String>) -> Config {
    Config { query: String::from(&args[1]), file_path: String::from(&args[2]) }
}
```

>We’ve added a struct named `Config` defined to have fields named `query` and `file_path`. The signature of `parse_config` now indicates that it returns a `Config` value. <u>In the body of `parse_config`, where we used to return string slices that reference `String` values in `args`, we now define `Config` to contain owned `String` values.</u>

At this point, it is necessary to pause and thoroughly understand the choices made in Code 12.3.2.

First of all, it should be emphasized that <u>Code 12.3.2 differs from the one proposed by the official book</u>. While the difference is subtle—given the few lines of code and its simple task—it remains fundamental to grasp.

The official book operates differently than `env::args().collect::<Vec<String>>()`. Specifically, it defines a variable named `args` of type `Vec<String>` directly inside the `main` function by calling `env::args().collect()` (as seen in Code 12.3.1). The underlying method used is identical to ours; the difference lies in the `::<Vec<String>>` syntax, which resolves the type of the collection built by `collect`. In the official book, this ambiguity is solved by the type annotation `: Vec<String>` in the definition of the `args` variable.

<Info>
### The Turbofish Operator `::<T>`

When Rust sees `<` and `>` in expression context (like right after a method name), its parser historically gets confused. By default, it might think `<` is a 'less-than' operator and `>` is a 'greater-than' operator, leading to syntax ambiguity.

To tell the parser: 'Stop, this is not math, these are generic type parameters!', Rust uses the `::` prefix.

The `collect` method is defined on the `Iterator` trait, and its job is to take a stream of items and shove them into some kind of collection.

Its signature looks roughly like this: `fn collect<B>(self) -> B`.

So, `env::args().collect::<Vec<String>>()` translates to:

'Take the arguments iterator, and explicitly execute the `collect` method by binding its generic type parameter `B` to `Vec<String>`.'

- `collect` $\rightarrow$ The method being called.
- `::` $\rightarrow$ The turbofish separator telling the compiler that generic arguments are coming.
- `<Vec<String>>` $\rightarrow$ The concrete type `B` that you are explicitly handing to the `collect` method.
</Info>

Now, we want to clarify why the official book operates this way and why our approach has been slightly modified.

<u>Since the vector containing all the command-line arguments provided by the user is not entirely necessary for `minigrep` (we only need `query` and `file_path`, though the user could type other arguments), it makes sense to avoid storing the entire `args` vector in `main`. Otherwise, it would unnecessarily occupy memory for the program's entire duration.</u> In reality, `args` might not be useless if `Config` were not defined. However, since this is the approach pursued by the book—and since it makes sense—the situation changes. <u>If both `args` and `config` were maintained in the `main` function, it would certainly result either in memory duplication or in references within `config` pointing back into `args`.</u>

Furthermore, <u>the book intends for `Config`'s fields to maintain ownership of their data in memory; indeed, `Config`'s fields are defined as type `String` rather than references</u>.

<Warning>
Although `String` is effectively (also) a pointer to the heap, variables of this type maintain full ownership of the data they point to!
</Warning>

Consequently, <u>since `config`'s fields own their data, they cannot be references. Therefore, in the official book, they must necessarily be independent copies of the data in memory!</u> The book resolves this data copying by using the `clone` method, which is already implemented for the `String` type (as `String` derives the `Clone` trait). Specifically, their implementation of `parse_config` is:

- `Config { query: args[1].clone(), file_path: &args[2].clone() }`

Considering the official book' solution, <u>the `args` variable in `main` owns the values `args[1]` and `args[2]` accessed in `parse_config`, and is only letting the `parse_config` function borrow them. This means we’d violate Rust’s borrowing rules if `Config` tried to take ownership of the values in `args` by MOVING them.</u> This is one of the most important things to understand about Rust' strict architectural constraints. <u>If we tried to 'extract' `query` and `file_path` from the vector inside `parse_config` (by moving them) we would invalidate the `args` vector in `main` because it would be left with missing elements (invalid indexes).</u> This is exactly the same behaviour that occurs with structs: <u>as soon as we move the ownership out of a struct's field, the struct itself becomes invalid</u>.

For this reason, <u>Rust generally encourages defining vectors once in the `main` function and then leveraging the power of slices to perform computations over that same collection defined in the wider scope</u>. This implies that, in practice, we shouldn't necessarily rely on the architecture of Code 12.3.2, nor the one used by the official book, which is ultimately forced to use `clone` inside `parse_config`.

Regarding this approach, it must be noted that <u>`{ query: String::from(&args[1]), file_path: String::from(&args[2]) }` performs cloning operations under the hood via `String::from`, doing exactly what the official book does, albeit more explicitly</u>.

Now, you might wonder what actually changes between Code 12.3.2 and the book solution, if we are still forced to make a hard copy in memory instead of moving or referencing the data. <u>The key difference is that we don't store a useless `args` vector in `main` for the entire duration of the program. Instead, we pass the expression `env::args().collect::<Vec<String>>()`, which evaluates to a vector of strings, directly into the `parse_config` function. As we saw in section 3.2, this vector is moved directly into the inner scope of the function, ensuring that its memory is freed as soon as the function ends.</u>

Finally, let's address the reason why we are forced to create a hard copy of `query` and `file_path` (in both code variants): <u>Because we store the vector of strings inside the inner scope of `parse_config`, we cannot return references to its elements; doing so would result in returning dangling references from the function. We also cannot MOVE those values out of the vector for the exact same reason analyzed previously in the `main` context: Rust strictly forbids extracting values directly out of collections via a move operation using indexing.</u>

<Info>
### The Trade-Offs of Using `clone`

><u>There’s a tendency among many Rustaceans to avoid using `clone` to fix ownership problems because of its runtime cost.</u> But for now, it’s okay to copy a few strings to continue making progress because you’ll make these copies only once and your file path and query string are very small.
</Info>

>We’ve updated `main` so that it places the instance of `Config` returned by `parse_config` into a variable named `config`, and we updated the code that previously used the separate `query` and `file_path` variables so that it now uses the fields on the `Config` struct instead.

>Now our code more clearly conveys that `query` and `file_path` are related and that their purpose is to configure how the program will work. Any code that uses these values knows to find them in the `config` instance in the fields named for their purpose.

### Creating a Constructor for `Config`

>Now that the purpose of the `parse_config` function is to create a `Config` instance, we can change `parse_config` from a plain function to a function named `new` that is associated with the `Config` struct. Making this change will make the code more idiomatic. We can create instances of types in the standard library, such as `String`, by calling `String::new`. Similarly, by changing `parse_config` into a `new` function associated with `Config`, we’ll be able to create instances of `Config` by calling `Config::new`. Code 12.3.3 shows the changes we need to make.

```rust Code 12.3.3
fn main() {
    let config = Config::new(env::args().collect::<Vec<String>>());

    // --snip--
}

// --snip--

impl Config {
    fn new(args: Vec<String>) -> Config {
        Config { query: String::from(&args[1]), file_path: String::from(&args[2]) }
    }
}
```

>We’ve updated `main` where we were calling `parse_config` to instead call `Config::new`. We’ve changed the name of `parse_config` to `new` and moved it within an `impl` block, which associates the `new` function with `Config`. Try compiling this code again to make sure it works.

### Returning a `Result` Instead of Calling `panic!` and Handling Errors

>We can instead return a `Result` value that will contain a `Config` instance in the successful case and will describe the problem in the error case. We’re also going to change the function name from `new` to `build` because <u>many programmers expect `new` functions to never fail</u>. When `Config::build` is communicating to `main`, we can use the `Result` type to signal there was a problem. Then, <u>we can change `main` to convert an `Err` variant into a more practical error for our users without the surrounding text about `thread 'main'` and `RUST_BACKTRACE` that a call to `panic!` causes</u>.

>Code 12.3.5 shows the changes we need to make to the return value of the function we’re now calling `Config::build` and the body of the function needed to return a `Result`. To handle the error case and print a user-friendly message, we need to update `main` to handle the `Result` being returned by `Config::build`, as shown in Code 12.3.5. We’ll also take the responsibility of exiting the command line tool with a nonzero error code away from `panic!` and instead implement it by hand. <u>A nonzero exit status is a convention to signal to the process that called our program that the program exited with an error state.</u>

<CodeGroup>
```rust Code 12.3.5
use std::{env, fs, process};

fn main() {
    let config = Config::build(env::args().collect::<Vec<String>>()).unwrap_or_else(|err| {
        println!("Problem parsing arguments: {err}");
        process::exit(1);
    });

    // --snip--
}

struct Config {
    query: String,
    file_path: String,
}

impl Config {
    fn build(args: Vec<String>) -> Result<Config, &'static str> {
        if args.len() < 3 {
            return Err("not enough arguments");
        }
        Ok(Config { query: String::from(&args[1]), file_path: String::from(&args[2]) })
    }
}
```
```text E-Output 12.3.5
   Compiling minigrep v0.1.0 (/var/home/z561/rust_projects/minigrep)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.09s
     Running `target/debug/minigrep`
Problem parsing arguments: not enough arguments
```
</CodeGroup>

>Our build function returns a `Result` with a `Config` instance in the success case and a string literal in the error case. Our error values will always be string literals that have the `'static` lifetime.

>We’ve made two changes in the body of the function: <u>Instead of calling `panic!` when the user doesn’t pass enough arguments, we now return an `Err` value, and we’ve wrapped the `Config` return value in an `Ok`</u>. These changes make the function conform to its new type signature.

>Returning an `Err` value from `Config::build` allows the `main` function to handle the `Result` value returned from the build function and exit the process more cleanly in the error case.

>In Code 12.3.5 we’ve used a method we haven’t covered in detail yet: `unwrap_or_else`, which is defined on `Result<T, E>` by the standard library. Using `unwrap_or_else` allows us to define some custom, non-`panic!` error handling. If the `Result` is an `Ok` value, this method’s behavior is similar to `unwrap`: It returns the inner value that `Ok` is wrapping. However, if the value is an `Err` value, this method calls the code in the closure, which is an anonymous function we define and pass as an argument to `unwrap_or_else`. We’ll cover closures in more detail in Ch. 13. For now, you just need to know that `unwrap_or_else` will pass the inner value of the `Err`, which in this case is the static string `not enough arguments`, to our closure in the argument `err` that appears between the vertical pipes. The code in the closure can then use the `err` value when it runs.

>We’ve added a new `use` line to bring `process` from the standard library into scope. The code in the closure that will be run in the error case is only two lines: We print the `err` value and then call `process::exit`. The `process::exit` function will stop the program immediately and return the number that was passed as the exit status code. This is similar to the `panic!`-based handling, but we no longer get all the extra output.

>Great! E-Output 12.3.5 is much friendlier for our users.

## Extracting Logic from `main`

>Now that we’ve finished refactoring the configuration parsing, let’s turn to the program’s logic. <u>We’ll extract a function named `run` that will hold all the logic currently in the `main` function that isn’t involved with setting up configuration or handling errors.</u> When we’re done, the `main` function will be concise and easy to verify by inspection, and we’ll be able to write tests for all the other logic.

```rust Code 12.3.6
fn main() {
    // --snip--

    run(config);
}

fn run(config: Config) {
    let contents = fs::read_to_string(config.file_path)
        .expect("Should have been able to read the file");

    println!("With text:\n{contents}");
}

// --snip--
```

><u>The `run` function now contains all the remaining logic from `main`, starting from reading the file.</u> The `run` function takes the `Config` instance as an argument.

It is important to note that `config` is not passed as a reference to the `run` function. This means that, <u>since `Config` is not a struct that implements `Copy`, once `run` is called, `config` will be MOVED into the `config` variable within `run`'s inner scope—which, as observed in section 3.2, is a completely independent variable despite sharing the same name</u>. This implementation choice must ensure that <u>we will never need to use `config` in `main` again</u>, as the memory associated with it will be deallocated at the end of the inner scope (`run`), after its ownership has been transferred to the variable that shadows `config`.

### Returning Errors from `run`

>With the remaining program logic separated into the `run` function, we can improve the error handling. Instead of allowing the program to panic by calling `expect`, the `run` function will return a `Result<T, E>` when something goes wrong. This will let us further consolidate the logic around handling errors into `main` in a user-friendly way. Code 12.3.7 shows the changes we need to make to the signature and body of `run`.

<CodeGroup>
```rust Code 12.3.7
use std::{env, fs, process, error::Error};

// --snip--

fn run(config: Config) -> Result<(), Box<dyn Error>> {
    let contents = fs::read_to_string(config.file_path)?;
    
    println!("With text:\n{contents}");

    Ok(())
}
```

>We’ve made three significant changes here. First, we changed the return type of the `run` function to `Result<(), Box<dyn Error>>`. <u>This function previously returned the unit type, `()`, and we keep that as the value returned in the `Ok` case.</u>

>For the error type, we used the trait object `Box<dyn Error>` (and we brought `std::error::Error` into scope with a `use` statement at the top). `Box<dyn Error>` means the function will return a type that implements the `Error` trait, but we don’t have to specify what particular type the return value will be. This gives us flexibility to return error values that may be of different types in different error cases. <u>The `dyn` keyword is short for dynamic.</u>

>Second, we’ve removed the call to `expect` in favor of the `?` operator, as we talked about in Ch. 9. <u>Rather than `panic!` on an error, `?` will return the error value from the current function for the caller to handle.</u>

<Tip>
When the expression to which the `?` operator is applied does not return an error (meaning it succeeds), the `?` operator simply unwraps the inner value and allows execution to proceed normally.
</Tip>

>Third, the `run` function now returns an `Ok` value in the success case. We’ve declared the `run` function’s success type as `()` in the signature, which means we need to wrap the unit type value in the `Ok` value. This `Ok(())` syntax might look a bit strange at first. But <u>using `()` like this is the idiomatic way to indicate that we’re calling run for its side effects only; it doesn’t return a value we need</u>.

>When you run this code through `cargo run -- the poem.txt`, it will compile but will display a warning (E-Output 12.3.7).

>Rust tells us that our code ignored the `Result` value and the `Result` value might indicate that an error occurred. We’re not checking to see whether or not there was an error, and the compiler reminds us that we probably meant to have some error-handling code here! Let’s rectify that problem now.

### Handling Errors Returned from `run` in `main`

>We’ll check for errors and handle them using a technique similar to one we used with `Config::build`, but with a slight difference:

```rust Code 12.3.8
fn main() {
    // --snip--

    if let Err(e) = run(config) {
        println!("Application error: {e}");
        process::exit(1);
    }
}
```

>We use `if let` rather than `unwrap_or_else` to check whether `run` returns an `Err` value and to call `process::exit(1)` if it does. The `run` function doesn’t return a value that we want to `unwrap` in the same way that `Config::build` returns the `Config` instance. <u>Because `run` returns `()` in the success case, we only care about detecting an error, so we don’t need `unwrap_or_else` to return the unwrapped value, which would only be `()`.</u>

>The bodies of the `if let` and the `unwrap_or_else` functions are the same in both cases: We print the error and exit.

## Splitting Code into a Library Crate

>Our `minigrep` project is looking good so far! Now we’ll split the _src/main.rs_ file and put some code into the _src/lib.rs_ file. <u>That way, we can test the code and have a _src/main.rs_ file with fewer responsibilities.</u>

>Let’s define the code responsible for searching text in _src/lib.rs_ rather than in _src/main.rs_, which will let us (or anyone else using our `minigrep` library) call the searching function from more contexts than our `minigrep` binary.

>First, let’s define the `search` function signature in _src/lib.rs_ as shown in Code 12.3.9, with a body that calls the `unimplemented!` macro. We’ll explain the signature in more detail when we fill in the implementation.

```rust Code 12.3.9
pub fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {
    unimplemented!();
}
```

>We’ve used the `pub` keyword on the function definition to designate search as part of our library crate’s public API. We now have a library crate that we can use from our binary crate and that we can test!

>Now we need to bring the code defined in _src/lib.rs_ into the scope of the binary crate in _src/main.rs_ and call it, as shown in Code 12.3.10.

```rust Code 12.3.10
// --snip--
use minigrep::search;

fn main() {
    // --snip--
}

fn run(config: Config) -> Result<(), Box<dyn Error>> {
    let contents = fs::read_to_string(config.file_path)?;

    for line in search(&config.query, &contents) {
        println!("{line}");
    }

    Ok(())
}
```

>We add a `use minigrep::search` line to bring the `search` function from the library crate into the binary crate’s scope. Then, <u>in the `run` function, rather than printing out the contents of the file, we call the `search` function and pass the `config.query` value and `contents` as arguments</u>. Then, <u>`run` will use a `for` loop to print each line returned from `search` that matched the `query`</u>. This is also a good time to remove the `println!` calls in the `main` function that displayed the query and the file path so that our program only prints the search results (if no errors occur).

><u>Note that the `search` function will be collecting all the results into a vector it returns before any printing happens. This implementation could be slow to display results when searching large files, because results aren’t printed as they’re found</u>; we’ll discuss a possible way to fix this using iterators in Ch. 13.
