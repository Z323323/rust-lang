>A **struct**, or structure, is a custom data type that lets you package together and name multiple related values that make up a <u>meaningful group</u>.

>Structs are similar to tuples, in that both hold multiple related values. Like tuples, the pieces of a struct can be different types. Unlike with tuples, <u>in a struct you’ll name each piece of data so it’s clear what the values mean</u>.

>To define a struct, we enter the keyword `struct` and name the entire struct. A struct’s name should describe the significance of the pieces of data being grouped together. Then, inside curly brackets, we define the names and types of the pieces of data, which we call <u>fields</u>.

>For example, Code 5.1.1 shows a struct that stores information about a user account.

```rust Code 5.1.1
struct User {
    active: bool,
    username: String,
    email: String,
    sign_in_count: u64,   
}
```

><u>To use a struct after we’ve defined it, we create an instance of that struct by specifying concrete values for each of the fields.</u> We create an instance by stating the name of the struct and then add curly brackets containing `key: value` pairs, where the keys are the names of the fields and the values are the data we want to store in those fields.

```rust Code 5.1.2
fn main() {
    let user1 = User {
        active: true,
        username: String::from("someusername123"),
        email: String::from("someone@example.com"),
        sign_in_count: 1,
    };
}
```

>To get a specific value from a struct, we use dot notation. For example, to access this user’s email address, we use `user1.email`. <u>If the instance is mutable, we can change a value by using the dot notation and assigning into a particular field.</u> Code 5.1.3 shows how to change the value in the `email` field of a mutable `User` instance.

```rust Code 5.1.3
fn main() {
    let mut user1 = User {
        // --snip--
    };

    user1.email = String::from("anotheremail@example.com");
}
```

><p><u>Note that the entire instance must be mutable; Rust doesn’t allow us to mark only certain fields as mutable. As with any expression, we can construct a new instance of the struct as the last expression in the function body to implicitly return that new instance.</u></p>

>Code 5.1.4 shows a `build_user` function that returns a `User` instance with the given email and username.

```rust Code 5.1.4
fn build_user(email: String, username: String) -> User {
    User {
        active: true,
        username: username,
        email: email,
        sign_in_count: 1,
    }
}
```

>It makes sense to name the function parameters with the same name as the struct fields, but having to repeat the `email` and `username` field names and variables is a bit tedious. If the struct had more fields, repeating each name would get even more annoying. Luckily, there’s a convenient shorthand!

## Using the Field Init Shorthand

>In Code 5.1.5, using the field init shorthand syntax, <u>we set the `email` field’s value to the value in the `email` parameter of the `build_user` function</u>. <u>Because the `email` field and the `email` parameter have the same name, we only need to write `email` rather than `email: email`.</u>

```rust Code 5.1.5
fn build_user(email: String) -> User {
    User {
        // --snip--
        email,
    }
}
```

## Creating Instances with Struct Update Syntax

>It’s often useful to create a new instance of a struct that includes most of the values from another instance of the same type, but changes some of them. You can do this using struct update syntax.

>The syntax `..` specifies that <u>the remaining fields not explicitly set should have the same value as the fields in the given instance</u>.

```rust Code 5.1.6
fn main() {
    // --snip--

    let user2 = User {
        email: String::from("another@example.com"),
        ..user1
    };
}
```

>Code 5.1.6 creates an instance in `user2` that has a different value for `email` but has the same values for the `username`, `active`, and `sign_in_count` fields from `user1`. <u>The `..user1` must come last to specify that any remaining fields should get their values from the corresponding fields in `user1`</u>, but we can choose to specify values for as many fields as we want in any order, regardless of the order of the fields in the struct’s definition.

><p><u>In Code 5.1.6, we can no longer use `user1` after creating `user2` because the `String` in the `username` field of `user1` was moved into `user2`. If we had given `user2` new `String` values for both `email` and `username`, and thus only used the `active` and `sign_in_count` values from `user1`, then `user1` would still be valid after creating `user2`. This happens because both `active` and `sign_in_count` are types that implement the `Copy` trait. We can also still use `user1.email` in this example, because its value was not moved out of `user1`.</u></p>

Thanks to the comprehensive analysis conducted in Ch. 4, it is easy to imagine how a struct's field values are laid out on the stack; therefore, a detailed memory analysis will not be necessary in this case.

## Tuples vs Structs

As mentioned in the official book, tuples are somewhat similar to structs. In this section, we want to emphasize that <u>tuples and structs represent exactly the same thing at the raw data level</u>. The only difference between the two is that a struct's fields are assigned custom labels, allowing you to write clearer, more structured—and therefore more powerful—code using built-in language features (such as the `..` operator we just observed). In particular, Code 5.1.7, C-Output 5.1.7, Code 5.1.8, and C-Output 5.1.8 demonstrate that <u>tuples and structs behave completely identically with respect to the ownership mechanism</u>.

## Creating Different Types with Tuple Structs

>Rust also supports structs that look similar to tuples, called **tuple structs**. <u>Tuple structs have the added meaning the struct name provides but don’t have names associated with their fields; rather, they just have the types of the fields. Tuple structs are useful when you want to give the whole tuple a name and make the tuple a different type from other tuples, and when naming each field as in a regular struct would be verbose or redundant.</u>

>To define a tuple struct, start with the `struct` keyword and the struct name followed by the types in the tuple. For example, Code 5.1.1 defines and uses two tuple structs named `Color` and `Point`:

```rust Code 5.1.11
struct Color(i32, i32, i32);
struct Point(i32, i32, i32);

fn main() {
    let black = Color(0, 0, 0);
    let origin = Point(0, 0, 0);
}
```

>Note that the <u>`black` and `origin` values are different types</u> because they’re instances of different tuple structs. <u>Each struct you define is its own type</u>, even though the fields within the struct might have the same types. For example, a function that takes a parameter of type `Color` cannot take a `Point` as an argument, even though both types are made up of three `i32` values. Otherwise, <u>tuple struct instances are similar to tuples in that you can destructure them into their individual pieces, and you can use a `.` followed by the index to access an individual value</u>. Unlike tuples, <u>tuple structs require you to name the type of the struct when you destructure them</u>. For example, we would write `let Point(x, y, z) = origin` to destructure the values in the `origin` point into variables named `x`, `y`, and `z`.

## Defining Unit-Like Structs

>You can also define structs that don’t have any fields! These are called **unit-like structs** because they behave similarly to `()`, the unit type. <u>Unit-like structs can be useful when you need to implement a trait on some type but don’t have any data that you want to store in the type itself.</u> We’ll discuss traits in Ch. 10. Here’s an example of declaring and instantiating a unit struct named `AlwaysEqual`:

```rust Code 5.1.12
struct AlwaysEqual;

fn main() {
    let subject = AlwaysEqual;
}
```

>Imagine that later we’ll implement behavior for this type such that every instance of AlwaysEqual is always equal to every instance of any other type, perhaps to have a known result for testing purposes. We wouldn’t need any data to implement that behavior!

## Ownership of Struct Data

>In the `User` struct definition in Code 5.1.1, we used the owned `String` type rather than the `&str` string slice type. This is a deliberate choice because we want each instance of this struct to own all of its data and for that data to be valid for as long as the entire struct is valid.

><u>It’s also possible for structs to store references to data owned by something else, but to do so requires the use of **lifetimes**, a Rust feature that we’ll discuss in Ch. 10. Lifetimes ensure that the data referenced by a struct is valid for as long as the struct is.</u> Let’s say you try to store a reference in a struct without specifying lifetimes, like the following in Code 5.1.13; this won’t work:

```rust Code 5.1.13
struct User {
    active: bool,
    username: &str,
    email: &str,
    sign_in_count: u64,
}

fn main() {
    let user1 = User {
        active: true,
        username: "someusername123",
        email: "someone@example.com",
        sign_in_count: 1,
    };
}
```

>The compiler will complain that it needs lifetime specifiers:

As we observed in Ch. 4 and section 3.2, data bound to variables can easily be dropped from memory. Because of this, <u>Rust cannot allow a struct to hold references (pointers) to memory locations that might be uninitialized or already freed</u>. Keep in mind that `&str` is a fat pointer to a string on the heap. Therefore, <u>Rust must guarantee at compile time that the pointers stored in `_username` and `_email` point to memory areas that actually exist when the struct is declared</u>.

To enforce this, Rust requires the use of lifetime syntax, generally indicated as `'a` (though you can choose custom names like `'custom`, except for `'static`; what matters is the position and the leading `'`). In Code 5.1.14, we explicitly mark the `User` struct with the lifetime `'a` (`<'a>`), along with `_username` and `_email`. This explicitly dictates that <u>the `User` instance cannot, under any circumstances, live longer than the shortest-lived field it contains</u>.

If you think about it carefully, this behavior is closely related to what we saw in Code 5.1.7 and Code 5.1.8. Once the `hello` string is moved out, <u>that specific field loses ownership and becomes invalid, which consequently renders the parent struct or tuple unusable as a whole</u>. Conceptually, this means the struct `strct1` or the tuple `tup1` cannot remain fully valid any longer than the shortest-lived field they contain!

<p><u>The key difference in Code 5.1.14 is that tracking this validity becomes much harder for the compiler because `_username` and `_email` DO NOT own the data they point to. As a result, the compiler cannot simply rely on the 'standard' ownership mechanism. Instead, it requires us to explicitly establish a link between the deallocation of the memory areas pointed to by the struct's fields and the validity of the struct itself.</u></p>

If the `User` instance were allowed to outlive the data referenced by `_username` or `_email`, the memory for those pointers could be freed BEFORE the `User` instance is destroyed. <u>This would result in a `User` instance containing dangling pointers.</u> By strictly enforcing this lifetime rule, Rust completely prevents this scenario.

We can finally conclude this section by noting that <u>`"someusername123"` and `"someone@example.com"` are both string slices whose underlying data is hardcoded for the entire duration of the program's execution in the `.rodata` segment</u>, residing in the same memory area as the compiled code itself. In this specific case, the compiler immediately recognizes that the data referenced by both `_username` and `_email` will easily outlive any instance of `User`, as they possess the maximum possible lifetime (`'static`).

## Deep Dive: The Mechanics of Explicit Lifetimes

To fully grasp why the compiler demands lifetimes, it is crucial to understand that in Rust, a lifetime is not just a vague concept—it is a concrete part of the language's type system.

When we define a reference without an explicit lifetime, such as `&str`, the compiler implicitly assigns it a lifetime based on the scope in which it was created (this is known as Non-Lexical Lifetimes, or NLL). However, <u>whenever a reference is embedded within a struct, enum, trait, function, or method, the compiler must enforce strict lifetime guarantees to prevent dangling pointers, applying the exact same safety principles we explored in the previous paragraph</u>.

By introducing the `<'a>` syntax, we are effectively declaring a generic lifetime parameter. Just as a generic type parameter (`<T>`) allows a struct to hold different types of data, a generic lifetime parameter (`<'a>`) allows a struct to hold references with varying lifespans.

When we declare struct `User<'a>`, we are stating a rigorous rule for the Rust Borrow Checker:
'<u>For any instance of `User`, find the concrete scope of the data passed into `_username`, and the concrete scope of the data passed into `_email`. Calculate whichever scope is the shortest. That shortest scope is now the concrete value of `'a`, and this `User` instance is strictly forbidden from existing beyond the end of `'a`'.</u>

This mechanism is what allows Rust to achieve memory safety without a Garbage Collector. Instead of constantly checking memory validity at runtime, the Borrow Checker analyzes these lifetime constraints during compilation. If it detects any mathematical possibility that the struct could outlive `'a`—even by a single line of code—it throws a compilation error, absolutely guaranteeing that a dangling pointer can never exist in the compiled program.
