>Cargo is designed so that you can extend it with new subcommands without having to modify it. <u>If a binary in your `$PATH` is named `cargo-something`, you can run it as if it were a Cargo subcommand by running `cargo something`. Custom commands like this are also listed when you run `cargo --list`.</u> Being able to use `cargo install` to install extensions and then run them just like the built-in Cargo tools is a super-convenient benefit of Cargo’s design!

## Writing Your Own Cargo Extension

Any binary named `cargo-mytool` works. Here's a minimal example.

<Steps>
<Step title="Initializing the Extension Package">
```bash Command 14.5.11
cargo new cargo-hello --name cargo-hello
```
</Step>
<Step title="Implementing Argument Parsing">
```rust cargo-hello/src/main.rs
fn main() {
    // Cargo passes the subcommand name as the first argument, so skip it.
    let args: Vec<String> = std::env::args().skip(1).collect();
    println!("Hello from cargo-hello! Args: {:?}", args);
}
```
</Step>
<Step title="Installing and Registering the Subcommand">
```bash Command 14.5.12
cargo install --path .    # It appears in `cargo --list` immediately.
```
</Step>
<Step title="Executing and Testing the Custom Subcommand">
<CodeGroup>
```bash Command 14.5.13
cargo hello --name world
```
```text Output 14.5.13
Hello from cargo-hello! Args: ["--name", "world"]
```
</CodeGroup>
</Step>
</Steps>

## Passing Cargo Metadata to Extensions

When you build a custom Cargo extension, <u>your tool often needs to inspect the project it is running inside</u>. It might need to know about workspace members, dependency trees, target directories, or the exact file paths of source code.

Reading and parsing _Cargo.toml_ files manually across an entire workspace is complex and error-prone. Fortunately, Cargo has a built-in feature for this: `cargo metadata`.

When executed, Cargo outputs a comprehensive JSON structure detailing everything about the workspace graph via `--format-version 1`. To save you from parsing raw JSON strings yourself, the community provides the `cargo_metadata` crate, which wraps this command into clean, strongly-typed Rust structures.

### Adding the Dependency

First, <u>add the crate to your extension's _Cargo.toml_</u>:

```toml Cargo.toml
[dependencies]
cargo_metadata = "0.18"
```

### Querying the Workspace Metadata

Here is how you can use it in your code to inspect every package in the current workspace:

```rust Code
fn main() {
    // Executes `cargo metadata --format-version 1` under the hood.
    let metadata = cargo_metadata::MetadataCommand::new()
        .exec()
        .expect("Failed to get cargo metadata");

    // Iterate through every package present in the workspace.
    for package in &metadata.packages {
        println!("Found package: {} v{}", package.name, package.version);
        println!("Manifest path: {}", package.manifest_path);
    }
}
```

What This Gives You Access To:

By leveraging `cargo_metadata`, your extension gains complete programmatic awareness of:

- Every crate in the workspace, including their names, versions, and unique IDs.
- Exact file paths, allowing your tool to locate source files (_src/lib.rs_, _src/main.rs_) and configuration files on disk.
- The complete dependency graph, letting you see which packages depend on what internal or external crates, along with their active features.

## Best Practices for Extension Authors

1. <u>Prefix the binary with `cargo-` even inside the crate name</u>: `cargo-mytool`.
2. Skip `argv[0]` — Cargo passes the full subcommand name (e.g., `"mytool"`) as the first argument to your binary.
3. <u>Use `--` to separate Cargo flags from your own flags</u> in documentation: `cargo mytool -- --my-flag`.
4. Read `CARGO` env var for the path to the current Cargo executable if you need to invoke Cargo from within your extension.
