>Rust’s standard library includes a number of very useful data structures called collections. Most other data types represent one specific value, but collections can contain multiple values. <u>Unlike the built-in array and tuple types, the data that these collections point to is stored on the heap, which means the amount of data does not need to be known at compile time and can grow or shrink as the program runs.</u>

>We’ll discuss three collections that are used very often in Rust programs:

>- A **vector** allows you to store a variable number of values <u>next to each other</u>.
>- A string is a collection of characters.
>- A **hash map** allows you to associate a value with a specific key.

>The first collection type we’ll look at is `Vec<T>`, also known as a vector. Vectors allow you to store more than one value in a single data structure that puts all the values next to each other in memory. <u>Vectors can only store values of the same type.</u>

## Creating a New Vector

>To create a new, empty vector, we call the `Vec::new` function. For ex. `let v: Vec<i32> = Vec::new()` creates a new instance of a collection ready to store elements of type `i32` on the heap. Note that we added a type annotation here because we aren’t inserting any values into this vector; Rust wouldn’t know what kind of elements we intend to store otherwise. This is an important point. Vectors are implemented using **generics**; we’ll cover how to use generics with your own types in Ch. 10. For now, know that the `Vec<T>` type provided by the standard library can hold any type. When we create a vector to hold a specific type, we can specify the type within angle brackets.

>More often, you’ll create a `Vec<T>` with initial values, and Rust will infer the type of value you want to store, so you rarely need to do type annotation. Rust conveniently provides the `vec!` macro, which will create a new vector that holds the values you give it. For ex. `let v = vec![1, 2, 3]` creates a new `Vec<i32>` that holds the values `1`, `2`, and `3`. <u>The integer type is `i32` because that’s the default integer type.</u>

## Updating a Vector

>To create a vector and then add elements to it, we can use the `push` method, as shown in Code 8.1.1.

```rust Code 8.1.1
fn main() {
    let mut v = Vec::new();

    v.push(5);
    v.push(6);
    v.push(7);
    v.push(8);
    /*  .
        .
        .  */      
}
```

>As with any variable, if we want to be able to change its value, we need to make it mutable using the `mut` keyword.

## Reading Elements of Vectors

><p><u>There are two ways to reference a value stored in a vector: via indexing or by using the `get` method.</u> Code 8.1.2 shows both methods of accessing a value in a vector.</p>

<CodeGroup>
```rust Code 8.1.2
fn main() {
    let v = vec![1, 2, 3, 4, 5];

    let third: &i32 = &v[2];
    println!("The third element is {third}");

    let third: Option<&i32> = v.get(2);
    match third {
        Some(third) => println!("The third element is {third}"),
        None => println!("There is no third element."),
    }
    
    let three = *(third.unwrap());
    
    println!("{three}");
}
```

>Note a few details here. We use the index value of `2` to get the third element because vectors are indexed by number, starting at zero. Using `&` and `[]` gives us a reference to the element at the index value. When we use the `get` method with the index passed as an argument, we get an `Option<&T>` that we can use with `match`.

This example is useful for highlighting some important details that the official book glosses over. First, `third` is shadowed twice. The first time, it transforms from the heap address of `3` into `Some(address_of(3))`. The second time, it is shadowed within the inner scope defined by the `match` expression. This specific shadowing is crucial to understand: the use of `match` is fundamentally tied to `let` binding—in fact, as seen in Ch. 6, `if let` is essentially just a synthetic shorthand for `match` (and contains the `let` keyword).

In this case, `match` binds `third` to a new `third` <u>within the inner scope</u>, which will now contain `address_of(3)`. Because this new `third` is an entirely separate variable (as emphasized multiple times in section 3.2), it will be dropped at the end of the inner scope, and it can be used (inside the inner scope) on the right side of the `=>` operator. When that inner scope ends, the shadowed `third` variable is dropped, and the `third` variable in the outer scope safely remains `Some(address_of(3))`, as demonstrated by E-Output 8.1.2 and the `unwrap` method.

Recalling Ch. 6 once more, you could instead use the `let else` construct here to preserve the extracted three in the outer scope. Indeed, `let else` is a fundamental construct in Rust, designed for this exact scenario. It allows you to idiomatically extract values from `Option` or `Result` via `let` binding and, most importantly, <u>makes them accessible in the outer scope</u> (as shown in Code 8.1.3 and E-Output 8.1.3)!

<CodeGroup>
```rust Code 8.1.3
fn main() {
    let v = vec![1, 2, 3, 4, 5];

    let Some(addr_of_third) = v.get(2) else {
        panic!();
    };
    
    let three = *addr_of_third;
    
    println!("{three}");
}
```

>Rust provides these two ways (`get` and `&` + `[]`) to reference an element so that <u>you can choose how the program behaves when you try to use an index value outside the range of existing elements</u>. As an example, let’s see what happens when we have a vector of five elements and then we try to access an element at index 100 with each technique, as shown in Code 8.1.4.

<CodeGroup>
```rust Code 8.1.4
fn main() {
    let v = vec![1, 2, 3, 4, 5];
    
    // let elem = &v[100]; // panics

    let Some(_elem) = v.get(100) else {
        println!("Do something! ... or");
        panic!();
    };
}
```

>When we run this code, <u>the first `[]` method will cause the program to panic because it references a nonexistent element (this is exactly the same behavior we saw with arrays!)</u>. This method is best used when you want your program to crash if there’s an attempt to access an element past the end of the vector.

><u>When the `get` method is passed an index that is outside the vector, it returns `None` without panicking.</u> You would use this method if accessing an element beyond the range of the vector may happen occasionally under normal circumstances. <u>Your code will then have logic to handle having either `Some(&element)` or `None`, as discussed in Ch. 6.</u> For example, the index could be coming from a person entering a number. If they accidentally enter a number that’s too large and the program gets a `None` value, you could tell the user how many items are in the current vector and give them another chance to enter a valid value. That would be more user-friendly than crashing the program due to a typo!

>When the program has a valid reference, the borrow checker enforces the borrowing rules covered in Ch. 4, to ensure idiomatic use of references to the contents of the vector. In Code 8.1.5, we hold an immutable reference to the first element in a vector and try to add an element to the end. This program won’t work if we also try to refer to that element later in the function.

<CodeGroup>
```rust Code 8.1.5
fn main() {
    let mut v = vec![1, 2, 3, 4, 5];

    v.push(6); // 'v' is modified here. -------------------------------------- error
              //                                                                   \
    println!("The first element is: {first}"); // Borrowed value 'first' read here. \

```

>This error is due to the way vectors work: Because vectors put the values next to each other in memory, <u>adding a new element onto the end of the vector might require allocating new memory and copying the old elements to the new space</u>, if there isn’t enough room to put all the elements next to each other where the vector is currently stored. <u>In that case, the reference to the first element would be pointing to deallocated memory.</u> The borrowing rules prevent programs from ending up in that situation.

It might seem that this last snippet from the official book clashes with the borrowing rules explained in Ch. 4. However, considering that <u>the Rust compiler also flags this identical pattern as an error when working with arrays</u> (as proved in Ch. 4)—even though arrays have a fixed size and cannot be reallocated on the stack—one might question what the underlying truth is.

<u>The reality is that both the explanation based on idiomaticity and the official book's rationale are correct.</u> In the case of arrays, memory reallocation does not occur; nevertheless, because the code violates a core Rust programming pattern, the compiler still rejects it as an error.

## Iterating Over the Values in a Vector

>To access each element in a vector in turn, we would iterate through all of the elements rather than use indices to access one at a time. Code 8.1.6 shows how to use a `for` loop to get immutable references to each element in a vector of `i32` values and print them.

```rust Code 8.1.6
fn main() {
    let v = vec![100, 32, 57];
    for i in &v {
        println!("{i}");
    }
}
```

>We can also iterate over mutable references to each element in a mutable vector in order to make changes to all the elements. The `for` loop in Code 8.1.7 will add `50` to each element.

```rust Code 8.1.7
fn main() {
    let mut v = vec![100, 32, 57];
    for i in &mut v {
        *i += 50;
    }
}
```

## Using an Enum to Store Multiple Types

>Vectors can only store values that are of the same type. This can be inconvenient; there are definitely use cases for needing to store a list of items of different types. Fortunately, the variants of an enum are defined under the same enum type, so when we need one type to represent elements of different types, we can define and use an enum!

>We’ve demonstrated this in Code 8.1.8.

```rust Code 8.1.8
enum SpreadsheetCell {
    I32(i32),
    F64(f64),
    String(String),
}

fn main() {
    let row = vec![
        SpreadsheetCell::I32(3),
        SpreadsheetCell::String(String::from("blue")),
        SpreadsheetCell::F64(10.12),
    ];
}
```

Earlier, I pointed out that tuple-struct variants introduce a certain degree of redundancy regarding both code readability and syntax. Consequently, one might ask whether a superior, more concise method exists to rewrite Code 8.1.8. Technically, an alternative does exist, but it is not necessary an improvement over the method demonstrated above (this alternative is linked to the `dyn` keyword and will be examined later).

Despite appearing as just another basic example, this snippet underscores one of Rust's shortcomings: the absence of concise syntax for such scenarios. This 'weakness', which is practically limited to code verbosity, is a direct result of Rust's lack of classical inheritance. Bypassing inheritance and the standard Object-Oriented (OO) paradigm is actually a major strength for Rust; it prevents the deep architectural complexities of OO design while still preserving its core capabilities, as shown in Code 8.1.8.

Regarding Code 8.1.8, another critical observation must be made regarding memory layout. <u>An enum can represent different types because it reserves STACK memory equal to its largest variant (plus a small discriminant tag). If one variant holds a massive struct while the others are tiny, every single record in an array or vector will consume the memory of that massive struct, leading to severe memory bloat and redundancy.</u>

The alternative approach—using traits and the `dyn` keyword (e.g., `Vec<Box<dyn Trait>>`)—solves this specific memory bloat. It ensures that every record in the array occupies a uniform, small size on the stack (a 16-byte fat pointer), leaving the actual dynamically sized data on the HEAP.

However, this architectural shift introduces strict performance trade-offs:

- **Loss of Cache Locality**: <u>Enums keep data contiguous in memory, allowing the CPU to cache them efficiently. Trait objects force the CPU to follow pointers to random, scattered locations on the heap (pointer chasing), which severely degrades read and write speeds due to continuous cache misses.</u>
- **Allocation Overhead**: Every single record requires an individual heap allocation when created, whereas an array of enums allocates everything in one fast, contiguous block.
- **Dynamic Dispatch (Vtable)**: `dyn Trait` forces the program to look up method addresses in a virtual method table at runtime, adding execution overhead compared to the direct, static dispatch used by enums.

Ultimately, neither approach is universally superior. Enums guarantee blistering speed through contiguous memory but risk stack bloat if variant sizes are mismatched. **Trait objects** offer stack memory efficiency and unlimited extensibility at the cost of heap indirection. <u>The choice must be rigorously evaluated based on whether your specific application is bottlenecked by memory footprint or CPU execution speed.</u>

>Rust needs to know what types will be in the vector at compile time so that it knows exactly how much memory on the heap will be needed to store each element. We must also be explicit about what types are allowed in this vector. If Rust allowed a vector to hold any type, there would be a chance that one or more of the types would cause errors with the operations performed on the elements of the vector. Using an enum plus a `match` expression means that Rust will ensure at compile time that every possible case is handled, as discussed in Ch. 6.

><u>If you don’t know the exhaustive set of types a program will get at runtime to store in a vector</u>, the enum technique won’t work. Instead, <u>you can use a trait object</u>, which we’ll cover in Ch. 18.

>In addition to `push`, a <u>`pop` method removes and returns the last element</u>.

## Dropping a Vector Drops Its Elements

>Like any other `struct`, a vector is freed when it goes out of scope.

>When the vector gets dropped, all of its contents are also dropped, meaning the integers it holds will be cleaned up. The borrow checker ensures that any references to contents of a vector are only used while the vector itself is valid.
